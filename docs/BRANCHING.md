# Ветки, ревью и релизы

Страница правил для работы в команде. Короткая намеренно: длинные регламенты не
читают.

---

## Главное: `master` — это канал обновлений

Кнопка **Update** в дешборде принимает только помеченный релиз с вершины
`master`. Значит:

> **Слить в `master` = раздать всем машинам.**

Отсюда правило, из которого растут все остальные:

**`master` не бывает промежуточным состоянием.** Слияние и выпуск релиза — одно
действие, а не два. Ветка живёт до тех пор, пока не готова уехать людям.

Если что-то влито, но не выпущено, появляется окно, где `master` не соответствует
ни одному релизу — и `scripts/acl_release_check.py` это покажет красным.

---

## Одна фича — одна ветка

Имя ветки называет **то, что увидит человек**, а не файл, который правится.

```
feature/one-file-install      ✓ понятно и через месяц
feature/setup-wizard          ✓
fix/tracking-link-wipe        ✓
feature/app-py-refactor       ✗ ничего не говорит
```

Префиксы: `feature/` — новое, `fix/` — починка. Ветки инструментов разработчика
приходят как `codex/*`, это нормально.

**Держите ветки короткими.** Наглядный урок: `codex/acl-windows-installer-v1`
прожила три дня и отстала на 27 коммитов — её содержимое уже нельзя было ставить
людям, хотя сама работа была правильной.

---

## Отдельная папка на ветку, а не `git checkout`

В чекауте `C:\fb_agents` работают **две сессии агентов сразу** — дешборд и RPA.
Переключение ветки меняет файлы под второй сессией на ходу, а в дереве у неё
почти всегда есть незакоммиченное. Так уже был потерян
`src/fb_ads_rpa/obsidian_sync.py`.

Поэтому:

```bash
git worktree add ../acl-setup-wizard -b feature/setup-wizard
```

Это не второй клон — одна история, разные папки, свой рабочий каталог у каждой
ветки. Закончили:

```bash
git worktree remove ../acl-setup-wizard
```

## Ревью

PR открывается **только на `MojoTheApe/adopy-campaing-launcher`** — это репозиторий,
куда смотрят разработчики. Push уходит во все три адреса, поэтому ветка появится
везде; два остальных — резервные копии, ревью там не ведётся.

### Готово к слиянию, когда

1. **сборка на вершине ветки зелёная** — не «была зелёной вчера»;
2. **на изменение есть тест**, и он проверен обратным ходом: со старым кодом
   падает. Тест, который проходит и до починки, ничего не охраняет;
3. **ветка трогает установку или лаунчер → прогнана на живой машине.** Песочница
   с заглушками ловит логику, но не ловит настоящий `winget`, настоящий клон и
   вход в GitHub;
4. **готов абзац для `docs/RELEASES.md`** — человеческим языком, что изменилось.

Пункт 4 не формальность: `RELEASES.md` — единственное место, которое отвечает на
вопрос «в какой версии эта фича».

## Слияние и релиз

```bash
# ветка влита перемоткой — расхождений быть не должно
git branch -f master <коммит>
git tag -a acl-release-ГГГГ-ММ-ДД -F -   # в аннотации: коммит, номер и ссылка на сборку
git push origin master
git push origin refs/tags/acl-release-ГГГГ-ММ-ДД
python scripts/acl_release_check.py       # должно сойтись
```

Аннотация тега обязана содержать **номер прогона сборки, слово `success` и ссылку
на него** — без этого `scripts/acl_update_gate.py` откажется ставить релиз на
машину байера. Это не бюрократия, а то, что мешает раскатать на десять человек
ветку, которая не собиралась.

Если в один день выходит несколько релизов — суффикс буквой: `…-09-03b`, `…-09-03c`.

---

## Как понять, о какой версии речь

| Вопрос | Ответ |
|---|---|
| Что вошло в релиз | `docs/RELEASES.md` |
| Какая версия стоит у этого человека | шапка дешборда, рядом с датой |
| Вышла ли уже эта починка | `git tag --contains <коммит>` |
| Чем отличаются два релиза | `git log --oneline acl-release-A..acl-release-B` |

---

## Чего не делать

- **не сливать в `master` «на посмотреть»** — это раздача;
- **не переключать ветки в общем чекауте** — см. выше про две сессии;
- **не держать ветку неделями** — она отстанет быстрее, чем кажется;
- `git stash`, `git checkout .`, `git reset --hard`, `git clean` — запрещены
  всегда, см. `CLAUDE.md`.

---

## Связанное

- `CLAUDE.md` — владение файлами, жёсткие запреты git, три push-адреса
- `docs/RELEASES.md` — что в каком релизе
- `docs/DISTRIBUTION.md` — что уезжает байеру
- `scripts/acl_release_check.py` — сверка релиза, тега и сборки
- `scripts/acl_update_gate.py` — что машина байера согласна принять
