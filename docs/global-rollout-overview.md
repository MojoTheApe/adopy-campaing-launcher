# Global Rollout — обзорный документ

Входная точка для разработчиков, которые будут переводить fb_agents
из личного инструмента одного человека в общий рабочий инструмент
компании. Читать этот документ первым; он ссылается на детальные
спеки по каждой части.

## Зачем (бизнес-контекст)

Сейчас дашборд и вся автоматизация публикации кампаний (Agent 10,
RPA через Multilogin + Playwright) работают **только локально**, на
машине одного человека, вручную. Компания хочет:

1. Дашборд — на домене, доступен всей команде.
2. Общая база данных — одна на всех, а не локальные файлы/CSV/Sheets
   у каждого своя копия.
3. Возможность для **любого сотрудника** запускать создание кампаний
   (RPA-публикацию) со своей машины, своими аккаунтами.

## Важное разграничение: две отдельные инициативы

В репозитории уже есть черновая спека `service-architecture.md` —
она про превращение аналитической части (Agent 1: анализ Excel →
связки → отчёты) в **per-customer** Docker-сервис с отдельным SQLite
на клиента. Это **другая** задача — про продажу инструмента внешним
клиентам как SaaS.

Этот документ и `hub-agent-architecture.md` — про **внутренний**
мульти-пользовательский рабочий инструмент для одной компании: общая
БД на всех сотрудников, распределённая RPA-публикация кампаний.
Не путать и не смешивать при реализации — разная модель изоляции
данных (per-customer vs shared-internal), разные приоритеты.

## Текущее состояние (as-is)

Основано на аудите кода на 2026-07-22:

| Компонент | Сейчас |
|---|---|
| Дашборд | FastAPI + Jinja2 (`src/web/app.py`), запускается локально через `serve.py` / `start_dashboard.bat`, порт 9090 |
| Хранилище данных | Смесь: локальные CSV (`config/ad_account_map.csv`), локальный JSON (`config/knowledge_base.json`), локальные SQLite (`data/content_machine.db`, `data/knowledge_context.db`), Google Sheets (цели/аккаунты через `GSHEET_*` в `.env`) |
| RPA-публикация (Agent 10) | Python + Playwright, подключается через CDP к **локально открытому** Multilogin-профилю на этой же машине; выполняется в том же процессе, что и запрос дашборда или CLI-скрипт |
| Секреты | Один `.env` в открытом виде (Anthropic/OpenAI/Gemini ключи, Google credentials, Multilogin launcher URL) — общий на всё, что запускается на этой машине |
| Пользователи | Один человек (ты), никакой модели "кто есть кто" в коде нет |
| Обновление кода | `git pull` вручную |

## Целевое состояние (to-be)

**Модель: hub + локальные агенты.**

```
                    ┌─────────────────────────┐
                    │   Hub (на домене)        │
                    │  ─ Общий дашборд         │
                    │  ─ Общая БД              │
                    │  ─ Job Queue API         │
                    └───────────┬─────────────┘
                                │ HTTPS, агент опрашивает
                    ┌───────────┴─────────────┐
                    │                         │
          ┌─────────▼────────┐     ┌─────────▼────────┐
          │ Local Agent       │     │ Local Agent       │
          │ (машина юзера А)  │     │ (машина юзера Б)  │
          │ ─ Multilogin      │     │ ─ Multilogin      │
          │   (его аккаунты)  │     │   (её аккаунты)   │
          │ ─ Playwright RPA  │     │ ─ Playwright RPA  │
          └───────────────────┘     └───────────────────┘
```

Детальная техническая спека этой модели — `hub-agent-architecture.md`.
Стратегия обновления кода агента на машинах сотрудников —
`agent-update-strategy.md`.

## Фазы раскатки

Соответствуют "кольцам" из `agent-update-strategy.md`, но на уровне
всего проекта, а не только обновления кода:

### Фаза 0 — сейчас
Всё локально, один человек. Активная разработка/калибровка RPA-флоу
на живом тестовом аккаунте (см. историю сессий по Agent 10).

### Фаза 1 — Hub MVP + пилот (рекомендуемый следующий шаг)
- Поднять hub: общий дашборд + общая БД (см. открытые вопросы ниже
  по хостингу).
- Мигрировать шаренные данные (`ad_account_map.csv`, знания/таргетинг)
  в общую БД — с привязкой "аккаунт → назначенный сотрудник".
- 2-3 человека ставят локального агента (git-based обновление,
  вариант 1 из `agent-update-strategy.md`), пробуют реальный флоу
  "запросил кампанию на дашборде → она выполнилась на его машине".
- Собрать обратную связь, посчитать реальную частоту сбоев (Meta UI
  живёт своей жизнью — см. заметки о нестабильности ниже).

### Фаза 2 — Раскатка на всю компанию
- После того как Фаза 1 отработала стабильно.
- Решить: git-based обновление и дальше, или переход на Intune
  (вариант 4) — зависит от ответа IT.
- Формализовать доступы (кто видит какие аккаунты, кто может
  запускать публикацию).

### Фаза 3 — Наблюдаемость и укрепление
- Централизованный сбор логов/скриншотов со всех агентов на hub.
- Мониторинг очереди задач (застрявшие/просроченные задачи).
- Обработка troubling-паттернов у Meta (см. ниже).

## Важное операционное наблюдение (не игнорировать при планировании)

В ходе калибровки RPA-флоу на одном тестовом аккаунте сегодня
(2026-07-22) после ~50+ быстрых подряд созданий тестовых кампаний
аккаунт стал вести себя нестабильно: страницы зависали на "Loading...",
некоторые UI-секции переставали рендериться. Это могло быть:
(a) обычная неполадка страницы, (b) реальное дросселирование/защита
от спама со стороны Meta для этого конкретного аккаунта.

**Вывод для мульти-пользовательской раскатки:** если много сотрудников
одновременно начнут массово создавать кампании через RPA на реальных
аккаунтах, вероятность упереться в подобное поведение Meta растёт.
Стоит заложить в hub-архитектуру:
- Ограничение скорости постановки задач в очередь (rate limiting) на
  аккаунт, не только на пользователя.
- Понятную индикацию в дашборде "аккаунт сейчас нестабилен/недавно
  было много попыток" вместо молчаливых зависших задач.

## Открытые вопросы (нужно решение стейкхолдеров, не разработчиков)

Эти вопросы поднимались в обсуждении, ответа пока нет — их нужно
решить до того, как фиксировать конкретные технологии в спеке:

1. **Хостинг hub'а.** Azure (есть AzureAD-аккаунты на машинах) vs
   другой облачный провайдер vs уже существующая инфраструктура
   компании.
2. **Auth на дашборде.** Google/Microsoft SSO vs собственная система
   логин/пароль.
3. **Масштаб и темп раскатки.** Пилот на небольшой команде vs сразу
   вся компания.
4. **Обновление кода агента.** git-based (вариант 1) достаточно
   надолго, или сразу выяснять реальность Intune (вариант 4) —
   см. `agent-update-strategy.md`.

До получения ответов детальная спека (`hub-agent-architecture.md`)
оставляет эти точки помеченными как configurable/TBD, а не жёстко
фиксирует конкретного провайдера или auth-механизм.
