# ACL Telemetry Hub — дизайн

Дата: 2026-11-17. Владелец решения: Евгений. Статус: черновик на согласование.

## 1. Зачем

Владелец хочет полностью управлять процессом работы байеров с ACL и видеть всё в
реальном времени:

- **чинить на ходу** — сбой у байера виден через минуты, а не на следующий день;
- **видеть, кто сколько открывает** — кампании по байерам, аккаунтам, дням;
- **отчётность по байерам** — «вчера Йотам за N часов открыл M кампаний, получил
  X лидов и Y депозитов»;
- **лучшие практики** — какие сочетания (гео, формат, бюджет, время, машина) дают
  результат, а какие ломаются;
- **диагностика + исправления или советы** по каждому прогону.

Сейчас данные уже собираются (журнал ACL-2347: Worker `acl-event-log` на
бесплатном KV в личном аккаунте Cloudflare), но:

- отправка раз в час (лимит 1000 записей KV в сутки), поэтому «в реальном
  времени» невозможно;
- данные лежат пачками-файлами, смотреть их можно только скриптом на машине
  владельца после ручного `acl_log_pull.py`;
- нет визуального представления, нет уведомлений, нет связи с лидами/депозитами
  из BI, нет паспорта машины.

Факт на 17.11: в журнале 4 машины (Yotam, Gil, Evgeni-TEST, Evgeni), ~25 тыс.
событий за 16 дней, потерь нет. Поэтому клиентская часть работает — меняется
приёмник и всё, что после него.

## 2. Цели, не-цели, анти-цели

**Цели**

1. Событие с машины байера видно владельцу ≤ 3 минут после того, как оно
   произошло (сбой кампании — ≤ 1 минуты).
2. Одна веб-страница «Control Center» (телефон и компьютер): живая лента, байеры,
   прогоны, машины, разбор одного прогона.
3. Telegram-бот владельца: мгновенные алерты о сбоях, утренний дайджест по
   байерам, команды-запросы.
4. Ежедневный отчёт по байеру: время работы, задания, кампании (дошли / нет),
   лиды, депозиты (FTD), spend — из BI.
5. Для каждого сбоя — отпечаток (группировка), счётчик повторов по машинам и
   версиям, совет или известное исправление; для повторяющихся — сигнал завести
   задачу.
6. Раз в неделю — отчёт «лучшие практики» по накопленным прогонам и исходам.

**Не-цели (сейчас)**

- Управлять машинами байеров удалённо (перезапуск, команды) — только смотреть.
- Скриншоты, записи экрана, содержимое креативов, тексты сверх уже собираемого.
- Опрос Meta по таймеру (правило «не опрашивать живые аккаунты»).
- Замена Sentry: Sentry остаётся для исключений кода.

**Анти-цели (провал, даже если «работает»)**

- Секреты (токены Meta, прокси-логины, пароли) попадают в хаб или в Telegram.
- Телеметрия тормозит или ломает публикацию у байера (отправка блокирует задание,
  растёт память, падает дешборд без сети).
- Посторонний видит данные: страница или API без защиты, бот отвечает не владельцу.
- Владельца засыпает алертами: один и тот же сбой 20 раз подряд = 20 сообщений.
- Ложная зелень: задание `done`, а кампании не дошли (урок аудита 01.11).

## 3. Ограничения

- Корпоративный аккаунт Cloudflare компании (оплата через бухгалтерию). Тариф Workers Paid ($5/мес) — **рекомендация**: на бесплатном
  тарифе Worker получает 10 мс CPU на запрос, а распаковка и разбор пачки 512 КБ
  в него не укладываются; D1 free (100 тыс. записанных строк в сутки) хватает на
  ~10 машин, но без запаса.
- Клиент (`src/acl_event_log/`) — только стандартная библиотека + уже стоящий
  `psutil`. Отправка — только в фоновом потоке, задание её не ждёт.
- Контракт `POST /v1/batch` (gzip ndjson, `Authorization: Bearer
  <ACL_LIBRARY_TOKEN>`, `X-ACL-Machine`, `X-ACL-Batch`) не меняется: старые сборки
  у байеров начинают писать в хаб сменой одного адреса.
- BI MySQL доступен только с машины владельца (креды в его `.env`) — Worker к нему
  не ходит; исходы загружает скрипт владельца.
- Весь пользовательский текст (страница, бот) — на английском (правило ACL);
  комментарии в коде и документы — по-русски.
- Процесс репо: Issue в трекере до кода (заводит главная сессия трекера), ветка
  `work/acl-<N>-…` от `work/main` с `--no-track`, worktree, PR в main, пачки v2.

## 4. Архитектура

```
машины байеров (ACL дешборд)                     Cloudflare (новый аккаунт)
┌─────────────────────────┐   POST /v1/batch    ┌──────────────────────────────┐
│ writer → outbox ndjson  │ ──────────────────▶ │ Worker `acl-hub`             │
│ shipper: раз в 2 мин +  │   gzip, токен       │  ingest → D1 `events`        │
│ сразу при сбое/конце    │                     │  derive → runs/jobs/machines │
│ machine.profile, load   │                     │  alerts → Telegram           │
└─────────────────────────┘                     │  cron: зависшие, дайджест    │
                                                │  /api/* + Control Center UI  │
машина владельца                                │  (за Cloudflare Access)      │
┌─────────────────────────┐  POST /v1/outcomes  │  /tg/webhook — команды бота  │
│ acl_hub_outcomes.py     │ ──────────────────▶ │  D1 `outcomes`               │
│ (BI MySQL → агрегаты)   │   OWNER_KEY         └──────────────────────────────┘
│ acl_log_pull.py (архив) │ ◀── /api/events ──           │
└─────────────────────────┘                              ▼
                                                  Telegram владельца
```

Один Worker, одна база D1. Выбор D1 вместо KV/R2 — **моё решение**: нужны
запросы по полям (байер, аккаунт, день, исход), а KV их не умеет.

### 4.1 Данные в D1

| Таблица | Строка | Откуда |
|---|---|---|
| `events` | одно событие как есть (те же колонки, что `store.py`) | приём |
| `machines` | машина: байер, версия, последний сигнал, паспорт | heartbeat, `machine.profile` |
| `jobs` | задание: кто, аккаунт, когда, длительность, счётчики дошло/нет/не начато | `job.*`, `publish.result` |
| `runs` | попытка кампании: исход, `stop_kind`, ошибка, отпечаток, время, вызовы, создано/переиспользовано, id объектов | `publish.result/stats/spec` |
| `failures` | отпечаток сбоя: сколько раз, машин, версий, первый/последний, совет, статус | `runs` |
| `outcomes` | день × аккаунт × адсет × объявление: лиды, FTD, spend, net | BI-загрузчик |
| `alerts` | что и когда отправлено в Telegram (для антиспама) | алерты |
| `tokens` | sha256 токена библиотеки + время проверки | авторизация |

`heartbeat` в `events` не пишется (только обновляет `machines`) — иначе при
отправке раз в 2 мин он станет половиной базы.

### 4.2 Исход прогона (без ложной зелени)

- `ok` — `publish.result.success = true`;
- `not_started` — ошибка начинается с `Not started` (следствие другого сбоя,
  не считается отдельным сбоем);
- `failed` — всё остальное.

Задание в `jobs` получает `n_ok / n_failed / n_not_started`; «зелёное» = все
кампании `ok`.

### 4.3 Отпечаток сбоя

`fingerprint = sha1(stop_kind + "|" + normalize(error))[:12]`, где `normalize`
повторяет `src/failure_signatures.normalise_reason` (цифры, uuid, длинные hex →
метки, пробелы схлопнуты, 160 символов). Совет к отпечатку — из справочника
`failure_hints` (ручной, правит владелец), позже — дополняется ИИ-разбором.

### 4.4 Реальное время

- Клиент: `CYCLE_S = 120`; дополнительно будит отправку при `publish.result` с
  `success = false` и при `job.finished` (уже есть).
- Хаб: алерт отправляется прямо в обработке пачки, без ожидания cron.
- Cron раз в 5 мин: задание `started` без `finished` дольше 45 мин → алерт
  «stuck job»; машина, работавшая сегодня, молчит > 30 мин в рабочие часы
  байера → алерт «machine silent».

### 4.5 Control Center (страница)

Отдаётся тем же Worker, защищена Cloudflare Access (Zero Trust, вход по
одноразовому коду на почту владельца) — **моё решение**, чтобы не писать свою
авторизацию. Worker дополнительно проверяет JWT Access.

Экраны (английский UI):

1. **Live** — лента последних событий по всем машинам, обновление раз в 15 с;
   сбои красным сверху.
2. **Today / Buyers** — таблица байеров за выбранный день: часы работы, задания,
   кампании ok/failed/not started, медиана времени кампании, лиды, FTD, spend.
3. **Buyer** — один байер: дни, аккаунты, прогоны, его машина и паспорт.
4. **Run** — одна кампания: шаги, время, вызовы Meta, ошибка простым текстом,
   отпечаток, сколько раз он встречался, совет.
5. **Failures** — отпечатки по частоте, машины/версии, статус (new / tracked /
   fixed), ссылка на задачу.
6. **Machines** — версия, последний сигнал, ящик, паспорт (RAM, CPU, Windows,
   экран, MLX/AdsPower), нагрузка в момент сбоев против успехов.

### 4.6 Telegram-бот

Отвечает только `chat_id` из `TG_ALLOWED_CHATS`. Webhook с секретом
(`X-Telegram-Bot-Api-Secret-Token`).

- **Алерты**: сбой кампании (байер, аккаунт, кампания, простой текст, отпечаток,
  «3-й раз за день на 2 машинах»), зависшее задание, молчащая машина, чекпоинт.
  Антиспам: один отпечаток на одну машину — не чаще раза в 30 мин, дальше
  счётчик в следующем сообщении.
- **Дайджест** 07:00 по Израилю: вчера по каждому байеру (часы, кампании ok/всего,
  лиды, FTD), топ-3 отпечатка, машины без сигнала.
- **Команды**: `/today`, `/buyer <имя>`, `/run <job_id>`, `/failures`,
  `/mute <fingerprint> <часы>`.

### 4.7 Исходы из BI (лиды и депозиты)

`scripts/acl_hub_outcomes.py` на машине владельца (планировщик Windows, раз в
час): читает `BI_Export.UF.Export` за последние 3 дня через
`src/analysis_agent/bi_stats` (только SELECT), агрегирует по
`DATE × ACCOUNT_ALIAS × ADSET_NAME × AD_TITLE`, шлёт в `POST /v1/outcomes`
(ключ `OWNER_KEY`). Связь с прогонами: `runs.account` + имена адсетов/объявлений
из `publish.spec` + дата (id кампании в BI нет — так решено в аудите 01.11).
Байер ↔ `CM_ID` — через `config/bi_cm_map.json`.

### 4.8 Диагностика, советы, лучшие практики

- Сразу: справочник подсказок по отпечаткам + правило «3 раза или 2 машины →
  предложить задачу» (из аудита 01.11).
- Паспорт машины (`machine.profile`, раз в запуск дешборда) и нагрузка (CPU,
  память, число профилей/вкладок) в `publish.stats` — и при успехе, чтобы было с
  чем сравнивать.
- Раз в неделю cron собирает сводку (прогоны + исходы по байерам, гео, формату,
  бюджету, времени суток, машине) и отправляет её в Claude API с просьбой
  выделить закономерности; ответ — в Telegram и на вкладку **Insights**.
  Модель — `claude-opus-5-5`, ключ — секрет Worker. Сырые события в ИИ не
  уходят, только агрегаты.

## 5. Безопасность и приватность

- Клиент уже чистит payload (`clean.py`: ссылки → отпечаток, без токенов);
  хаб при приёме повторно проверяет регэкспом `EAA…|access_token=` и такие
  события отклоняет с пометкой (не пишет).
- Запись — токен библиотеки (как сейчас), чтение — Cloudflare Access + JWT,
  загрузка исходов — `OWNER_KEY`, бот — секрет webhook + allowlist чатов.
- Все секреты — `wrangler secret put`, в репо только имена.
- Байеров предупреждаем, что собирается (короткий текст в README установки).

## 6. Порядок работ (отдельные планы)

| # | Часть | Даёт владельцу | Зависит от |
|---|---|---|---|
| 1 | **Хаб: приём в D1 + выводы (runs/jobs/machines) + быстрый клиент + паспорт машины + перенос истории** | данные с машин в реальном времени в одной базе | — |
| 2 | Control Center (страница + Access) | видеть всё визуально | 1 |
| 3 | Telegram-бот (алерты, дайджест, команды) | узнавать о сбоях сразу | 1 |
| 4 | Исходы из BI + отчёт по байеру | лиды/депозиты по байеру и дню | 1 (2/3 для показа) |
| 5 | Отпечатки, справочник советов, задачи, Insights (ИИ) | диагностика и лучшие практики | 1, 4 |

2 и 3 можно делать параллельно после 1. Подробный план — только для части 1;
следующие пишутся после её вливания, потому что опираются на схему D1.

## 7. Что решает владелец / что оставлено исполнителю

Решения владельца (уже приняты): Cloudflare, новый корпоративный аккаунт,
визуальная страница, Telegram-бот, отчёт байеров с лидами и депозитами.

Мои решения (владелец может изменить): D1 вместо KV; один Worker на всё;
Cloudflare Access для страницы; отправка раз в 2 мин; английский UI; Claude
`claude-opus-5-5` для недельной сводки; дайджест в 07:00 по Израилю; антиспам
30 мин.

Открытые вопросы владельцу:

1. Кто ещё, кроме вас, должен видеть страницу и получать бот (Дима? тимлиды)?
2. Показывать ли байеру его собственную статистику (позже, отдельная страница)?
3. Рабочие часы байеров для алерта «машина молчит» — одни на всех или свои?
