# Как записывать действия через уже открытый Multilogin-профиль

**Обновление 2026-07-23 (v2): Вариант B ниже (Playwright Inspector /
`page.pause()`) был реализован, подключён к дашборду, и вживую проверен —
и не работает на антидетект-браузере Multilogin (Mimic).** Оставлен в
документе только как предостережение — не пытаться снова без новых
оснований. **Вариант A — единственный подтверждённо рабочий способ**,
дашборд уже переключён обратно на него.

Обычный `playwright codegen <url>` открывает **свой собственный, новый**
Chromium — не тот, что управляется Multilogin. Это плохо по двум причинам:

1. **Безопасность.** Новый браузер не залогинен в Facebook — если логиниться
   заново прямо во время записи, пароль попадает в сгенерированный файл в
   открытом виде. Это уже случалось дважды в одной из прошлых сессий, оба
   файла пришлось удалить (см. `agent10-post-conversion-location-handoff.md`).
2. **Антидетект.** Meta видит запись как совершенно новое устройство/браузер
   без истории профиля — не тот "отпечаток", что настроен в Multilogin для
   этого аккаунта.

## Вариант A (единственный подтверждённо рабочий): `click_recorder.py`

`src/fb_ads_rpa/click_recorder.py`:

- Подключается через CDP к уже открытому браузеру. Теперь умеет найти
  правильный порт двумя способами: `_find_cdp_url_for_account(account_label)`
  (точный поиск через `ad_account_map.csv` → `profile_id` →
  `DevToolsActivePort`, добавлено 2026-07-23 — см. ниже почему) или
  `_find_cdp_url()` (грубый скан списка известных портов, как раньше).
- Внедряет **простой** JS-слушатель кликов/изменений/клавиш
  (`document.addEventListener('click', ..., true)`) прямо в открытую
  вкладку — без открытия нового окна.
- Пишет JSON-"рецепт" в `output/rpa_recipes/` с полем `own_text`, `role`,
  `aria_label`, `css_path`, координатами.

**Подтверждено вживую 2026-07-23**: этот механизм реально ловит клики на
Multilogin/Mimic-браузере (пример: поймал клик по "Further limit the reach
of your ads" с `own_text`, `role=""`, `css_path` — точные данные, которые
не удавалось получить никаким другим способом весь день).

Управляется через дашборд, кнопка **"⏺ Record clicks"**
(`POST /rpa-record/start {recipe_name?, cdp_url?, account_label?}`, `/stop`,
`GET /status`, `/recipes`).

**Минус:** выдаёт JSON с описанием действий, а не готовый Playwright-код
(`page.get_by_role(...).click()`) — для переноса в `meta_dom.py` всё равно
нужно вручную превратить описание в селектор. На практике это не помеха:
именно так и был перенесён шаг "Further limit the reach of your ads →
Continue" — по `own_text`/`role` из JSON-рецепта в надёжный own-text +
CDP-click паттерн (`_cdp_mouse_click`), уже проверенный на Website/Lead.

## Вариант B (проверено вживую 2026-07-23 — НЕ РАБОТАЕТ): `page.pause()` Inspector

Идея была: Playwright умеет открыть **Inspector** (окно с живой генерацией
кода, как у `codegen`) на уже существующей странице через
`connect_over_cdp()` + `page.pause()`, без второго браузера и без
повторного логина.

Реализовано (`src/fb_ads_rpa/codegen_recorder.py`, роуты `/rpa-codegen/*`),
подключено к дашборду, и опробовано вживую на аккаунте `FacebookDQ204 CR`:

- CDP-подключение проходило успешно (после фикса поиска порта — см. ниже).
- Inspector реально открывался, окно профиля подсвечивалось при переключении
  Record.
- **Но:** ни "Pick locator" (наведение на элемент), ни "Record" (клики) не
  давали вообще никакого эффекта — ни подсветки при наведении, ни новых
  строк кода при клике. Проверено дважды, с явным включением кнопки Record
  (кружок становился красным — то есть режим включался), клики
  пользователя в браузере никак не отражались в Inspector.
- Тем временем **Вариант A**, подключённый к тому же самому CDP-порту в тот
  же момент, **ловил клики нормально**.

**Вывод:** дело не в CDP-подключении (оно работает) и не в порядке действий
пользователя — а именно во **внутреннем механизме Playwright Inspector**
(вероятно, домен CDP `Overlay`, на котором основана подсветка элементов и
захват действий в Inspector) — Multilogin/Mimic, судя по всему, блокирует
или видоизменяет что-то на этом уровне как часть антидетект-модификаций,
из-за чего конкретно эта функция Playwright тихо не работает, хотя обычная
скриптовая автоматизация (прямые CDP-команды, `Input.dispatchMouseEvent` и
т.п. — то, чем пользуется весь `run_recorded_campaign_flow`) на этом же
браузере работает весь день без проблем.

**Не пытаться снова без новой информации** (например, если Multilogin
обновит Mimic и явно заявит о совместимости с DevTools Overlay/Inspector).
Код `codegen_recorder.py` оставлен в репозитории (фикс поиска порта по
аккаунту в нём тоже рабочий и полезный сам по себе), но дашборд на него
больше не завязан.

## Как получить CDP-адрес уже открытого профиля (готовые функции, не гадать порт)

| Функция | Файл | Когда использовать |
|---|---|---|
| `_find_cdp_url_for_account(account_label)` | `click_recorder.py`, `codegen_recorder.py` | **Предпочтительно.** Точный поиск через `ad_account_map.csv` → `profile_id` → `DevToolsActivePort`. Добавлено 2026-07-23 после того, как `_find_cdp_url()` не нашёл порт активной тестовой сессии (её порт не входил в захардкоженный список) |
| `_find_cdp_url()` | `click_recorder.py` | Фоллбэк — грубый скан списка известных портов, не требует знать `profile_id` |
| `MultiloginAttachOnlyProvider().open(entry, account_label)` | `browser.py` | Полноценное подключение (с перезапуском профиля через MLX API при необходимости), а не только поиск порта |

## Итог

Единственный способ для обучения/переноса шагов в `meta_dom.py` на этом
антидетект-браузере — **Вариант A**: `click_recorder.py` через дашборд,
затем вручную превратить `own_text`/`role`/`css_path` из JSON-рецепта в
own-text + CDP-click селектор в коде, тем же способом, что уже использован
для всех подтверждённых шагов сегодня.
