# Совместная разработка ACL: Claude и Codex

Это проектный процесс для всех агентов и людей, работающих над ACL. Общие
принципы, требования к коду, порядок параллельной работы и шаблон передачи
хранятся в [AI_COLLABORATION.md](AI_COLLABORATION.md). Здесь уточняются правила
ACL; `AGENTS.md`, `CLAUDE.md` и `docs/BRANCHING.md` ссылаются на этот процесс.
Конкретные указания владельца задачи имеют приоритет над этим документом;
согласованные исключения записываются в PR вместе с оставшимися проверками.

Готовый промпт для Claude и инструкция для будущих проектов:
[CLAUDE_START_PROMPT.md](CLAUDE_START_PROMPT.md).

## Репозиторий и ветки

- Рабочий GitHub: `MojoTheApe/adopy-campaing-launcher`.
- Production и база обычных PR: **`master`**. Ветки `main` здесь нет.
- Не полагаться на GitHub default branch: она может отличаться от production.
  В PR и при создании рабочей копии явно указывать базу.
- Каждая задача получает отдельную ветку и рабочую папку. Для Codex использовать
  `codex/<задача>`; для остальных допустимы `feature/` и `fix/`.
- Перед началом получить актуальные refs, проверить `git status` и записать
  base SHA. Пример для новой изолированной копии:

  ```bash
  git fetch origin master
  git worktree add ../acl-example -b codex/example origin/master
  ```

Не переключать ветку, не сбрасывать файлы и не убирать незакоммиченную работу
в папке другой сессии. Не применять `git stash`, `git reset --hard`, `git clean`
или массовое восстановление дерева к общей рабочей папке. Стейджить только
явно перечисленные файлы своей задачи; не использовать `git add .` / `git add -A`.
Рабочую папку удалять только после проверки, что нужная работа сохранена.

Перед push проверить `git remote get-url --push --all origin` и указать ветку
явно. В некоторых исторических клонах были дополнительные push-адреса;
не добавлять, не удалять и не копировать их автоматически из старых инструкций.
Существующие адреса сохранять в рамках ранее согласованной конфигурации клона.

## Задача, автор и ревьюер

Текущее распределение работы владельца проекта: Claude добавляет новые
функции в отдельные ветки; Codex проверяет их, исправляет найденные ошибки,
выполняет проверки и мержит подготовленный результат в `master` в рамках
согласованной задачи. Возвращать исправления Claude на обязательное повторное
ревью не требуется. Проверку собственных исправлений Codex описывает как
самопроверку; независимое ревью не заявляется, если его не было.

В задаче/PR зафиксировать:

1. Какую проблему решаем и какое поведение ожидается; что не входит в работу.
2. Какие ветки/коммиты входят в кандидат, base SHA и head SHA.
3. Кто реализует изменение и кто его проверяет; пересекающиеся файлы и ресурсы.
4. Критерии приёмки и команды проверок; требуемые ручные сценарии.

У конкретного изменения один автор. Второй агент проверяет результат и
возвращает воспроизводимые замечания. Он не переписывает те же файлы
одновременно с автором. Роли могут меняться между задачами и моделями.
Постоянной принадлежности `src/web` только Claude или `src/fb_ads_rpa` только
Codex нет: владельцы определяются текущей задачей. Разрешённые пользователем
сквозные исправления выполняются последовательно в своей копии.

Если нужен новый файл или участок чужой активной задачи, сначала сверить
владение. Не считать старую таблицу треков автоматическим запретом на
согласованную работу. При отсутствии реального пересечения продолжать задачу.

Основная карточка передачи в ACL — описание PR. До его появления использовать
короткую карточку в сообщении владельцу; связанную существующую задачу указать
ссылкой. Записывать исполнителя, область файлов, общие интерфейсы и ресурсы,
зависимости, статус и точный кандидат. Исторический план не доказывает текущее владение. Если
второй участник не имеет доступа к карточке, передать её через владельца;
не считать локальный файл автоматически видимым другой сессии.

После передачи кандидата Codex на ревью Claude продолжает новые функции
в другой ветке. Изменение проверяемого кандидата согласовывается; его новый SHA
должен быть проверен. После merge следующая независимая задача начинается
от актуального `master`, содержащего исправления ревьюера. Зависимость от
ещё не принятой функции записывается явно.

При изменении дашборда проверять потребителей маршрутов, DOM ID и событий,
включая корзину, раскрытие билдера, выбор страны/аккаунта, загрузку профилей,
старые ссылки и восстановление состояния, если они затронуты. Для кода RPA
сохранять draft-only и изоляцию профилей. Следовать существующим механизмам
навигации, конфигурации и ошибок; не добавлять независимые обработчики того
же состояния без необходимости.

Рекомендованный цикл:

`задача → отдельная ветка → небольшой PR → ревью и CI → исправления → master`.

Ревьюер читает фактический diff и требования. Согласие двух моделей не заменяет
тест. Спор разрешается примером входных данных и наблюдаемым результатом.
Если независимого ревью не было, это прямо указывается; нельзя выдавать
самопроверку автора за независимое ревью.

## Проверки

Для исправлений ошибок данных, конкуренции, установки и браузерной автоматики
добавлять проверки поведения. По возможности показать, что регрессионный
сценарий падает на старом коде и проходит после исправления. Проверки наличия
строк в исходнике недостаточно там, где можно выполнить обработчик или сценарий.
Небольшие правки текста и документации не требуют искусственных тестов.

Сначала запускать проверки затронутого участка, затем необходимую интеграцию.
Перед merge кода должны пройти проверки на итоговом кандидате:

```bash
python scripts/acl_scan_secrets.py
python scripts/acl_smoke.py
python -m pytest tests/ -q
```

CI выполняет их на **Windows / Python 3.11 и 3.13** для изменений продукта,
сборки, зависимостей и самого CI. Кандидат проверяется один раз на событии PR,
на дереве объединения его итогового head с актуальным `master`; дополнительного
дублирующего запуска на push в feature-ветку нет. После существенной
правки, разрешения конфликта или изменения базы старое зелёное CI не считается
проверкой нового результата. Для JS нужен Node; пропущенные проверки указывать
явно, особенно если локальная среда отличается от Windows.

По согласованной оптимизации расходов документация и метаданные трекера имеют
облегчённую проверку PR: scanner, JSON и тесты проектного tooling. Точный закрытый
список находится в `scripts/acl_ci_scope.py`: корневые документы, Markdown в
`docs/`, `tracker/config.json` и `tracker/engine.json`. Любой другой файл,
удаление/перемещение кода, отсутствующий diff или ошибка классификации сохраняют
полные Windows-проверки. Ошибка самого job классификации блокирует успешное CI;
Windows не выключается из-за отсутствующего output. Для лёгкого PR Windows jobs
имеют статус skipped, а не passed.

Push в `master` и ручной запуск всегда проверяют весь продукт и установщик,
включая изменения только документации. Это сохраняет подтверждение CI точного
SHA для release gate. Обязательные check names и защита ветки не отключаются.
Устаревшие запуски отменяются только в пределах одного workflow и PR/ref;
отменённый кандидат не считается проверенным. Для обратной связи до передачи
на ревью открывайте draft PR. Не запускайте заново успешный кандидат без новых
изменений, сбоя или конкретного нерешённого сомнения.

Для RPA, чистой установки и лаунчера нужен ручной Windows-пилот. Владелец может
явно перенести его после merge: зафиксировать это в PR и списке остающихся
проверок, выполнить все доступные автоматические проверки и не запрашивать
повторно уже данное разрешение. Не объявлять ручной сценарий пройденным.

## Изоляция данных и браузера

Worktree изолирует код, но не `.env`, OAuth-токены, порт dashboard, Multilogin,
CDP и открытые рекламные кабинеты. Тесты запускаются с отдельным
`ACL_CONFIG_DIR`, синтетическими данными и без обращений к рабочим аккаунтам.

- Один живой Multilogin-профиль одновременно обслуживает один ACL-процесс.
  Внутрипроцессная блокировка публикации/чтения не защищает от другой программы.
- Read и probe используют отдельную вкладку в подтверждённом профиле. Они
  не должны перезапускать профиль, менять кабинет или уничтожать черновик.
- Создание черновика и финальный Meta Publish — разные действия. Система
  остаётся draft-only; реальные публикации и бюджеты не являются unit-тестами.
- Машинные настройки, account map, токены, прокси, идентификаторы реальных
  кабинетов и диагностические артефакты не коммитятся. Использовать функции
  `config.paths`, а не пути конкретного пользователя. Шаблоны содержат только
  примеры. По умолчанию `output/**` остаётся локальным.
- Отправка telemetry — отдельное действие с авторизацией. Локальный сбор,
  наличие OAuth client, сохранённый write-token и успешная отправка — разные
  состояния; интерфейс и отчёт должны различать их.

## Merge и выпуск

Merge в `master` выполняется в пределах разрешённой пользователем задачи после
успешных обязательных проверок. Отдельное повторное подтверждение уже
согласованного merge не требуется. Не применять force push к production,
не отключать защиты и не обходить проваленные обязательные проверки.
Новые непроверенные коммиты не включаются в старое одобрение автоматически.

Владелец может явно согласовать исключение из проверки для конкретного PR.
В PR записать кандидата, причину, пропущенные проверки и ответственное лицо
за продолжение. Сбой Billing означает, что CI не запускался. Разрешение на
такой merge не переносится на будущие PR или продвижение релиза; защита ветки
и достоверность результатов сохраняются.

**Merge кода и продвижение релиза связаны, но технически различаются.**
Автообновление и однофайловый инсталлятор принимают только вершину
`origin/master` с аннотированным `acl-release-*` тегом и записью успешного CI.
Без подходящего тега инсталлятор отказывает, а новый релиз не предлагается.
Следовательно, один merge сам по себе не означает обновление всех машин.

Для продвижения релиза:

1. Зафиксировать состав и ограничения в `docs/RELEASES.md`.
2. Получить успешный CI на фактически выпускаемом SHA. Если GitHub создал
   merge commit, убедиться, что его дерево соответствует проверенному результату,
   и проверить CI самого merge commit перед выпуском.
3. Поставить аннотированный `acl-release-ГГГГ-ММ-ДД[суффикс]` тег на этот SHA.
   Аннотация содержит полный SHA, настоящее `success` и URL успешного Actions run.
   Не переиспользовать чужой run, не подменять тег, не записывать успех заранее.
4. Сверить gate и release metadata, выполнить пилотную установку и только затем
   рекомендовать массовое обновление. Если пилот отложен, явно указать это и
   согласованный объём продвижения; не называть такой выпуск проверенным на живой машине.

Разрыв между merge и продвижением нужно явно отражать в статусе задачи:
`код в master; релиз ещё не продвинут`. Не предлагать пользователям запуск нового
инсталлятора с непомеченной вершины канала. Уже опубликованные теги не менять;
исправления и откаты оформлять новыми проверяемыми коммитами/релизами.

## Таск-трекер: начало, очередь и завершение

Читайте [TRACKER_AGENT_WORKFLOW.md](TRACKER_AGENT_WORKFLOW.md), `tracker/config.json`
и актуальную общую инструкцию через `python scripts/task_tracker.py guide`.
Каждое поручение на разработку, включая «исправь сейчас», требует реального Issue:
`work ID` либо `work --title ... --body-file task.md --module ... --type ...` создаёт/находит задачу
и проверяет In Progress до первой правки кода. Агент выбирает модуль и тип сам;
планирование создаёт Idea/Backlog, а To Do содержит явно выбранную порцию работ.

Новое описание агент пишет сам на простом английском из запроса и проверенного
контекста: сначала `## Description` — что изменится, зачем и какой результат
ожидается; затем `## Specifications` — полный проверенный контекст для агента,
границы, критерии готовности, технические решения, проверки и текущая передача работы.
Читайте оба раздела целиком, независимо от свёрнутого состояния Specifications в UI. Используйте
`tracker/task-template.md`. Не придумывайте требования; исходное описание и
историю существующей задачи сохраняйте. Массовые ретроспективные правки — после
согласования примеров и проверки, что исходный Issue не изменился.

ID имеют префикс ACL: исторические номера сохранены, новые равны 1000 + номер Issue.
Приоритеты High / Medium / Low, по умолчанию Medium. Единая метка `release:included`
отображается как Release в Focus и включает задачу в виджет. Дополнительные
Required/MVP не нужны. Архив не означает завершение; merge не публикует релиз
и не очищает его состав. История выпуска сохраняется только после его явного подтверждения.

Перед merge укажите одну строку `Tracker issues: ACL-ID` с реальными ID и выполните
`python scripts/task_tracker.py check-pr PR_NUMBER`. После полного ревью и merge:

```sh
python scripts/task_tracker.py merged ID --pr PR_NUMBER
python scripts/task_tracker.py merged ID --pr PR_NUMBER --apply --reviewed-complete
```

Перечитайте метки и проверьте UI. Частичная задача остаётся в Review; нельзя
отмечать непроверенные чекбоксы ради прохождения проверки. Общая очередь разрешает
одну активную реализацию; перед следующим этапом оформляется передача через
`queue release ID`. Прежний `scripts/acl_mark_merged.py` сохранён для совместимости.
Проверки Windows и правила исключений выше действуют для каждого нового кандидата.

## Передача работы

Передавать ревьюеру ссылку на PR и короткую запись:

```text
Цель и ожидаемое поведение:
PR, base SHA, head SHA:
Включённые / исключённые изменения:
Закрываемые замечания (ID → исправление → тест):
Команды и результаты, URL CI:
Что не проверено / отложено и кем согласовано:
Следующее действие и ответственный:
```

Требования и результаты живут в репозитории/PR, а не только в пересказе чата.
Если команда ведёт Obsidian, журнал можно синхронизировать как вторую витрину;
он не должен быть единственным местом с контекстом и не должен требовать
жёстко заданного пути чужой машины. Не отправлять сообщения другим людям
или моделям без соответствующего разрешения пользователя.
