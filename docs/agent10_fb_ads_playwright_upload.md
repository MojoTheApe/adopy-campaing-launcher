# Агент 10: аплоуд рекламы в Facebook Ads Manager через Playwright (браузерная автоматизация)

Рисерч: как настроить агента, который **кликает кнопки в реальном интерфейсе Facebook Ads Manager** (создание кампании → адсет → объявление → загрузка креатива → публикация), и как его «обучать» новым флоу и чинить, когда FB меняет интерфейс.

Входные данные — уже готовый Excel из **агента 8** (`src/upload_agent/`) или строки из `upload_plan`/`upload_file` (см. `docs/service-architecture.md`, раздел 2.4). Одна строка плана = одна кампания/адсет/объявление, которое нужно реально создать в FB.

---

## 0. Главное решение, которое нужно принять до кода

Facebook даёт два пути создать кампанию программно:

| | **Marketing API** (Graph API, `POST /act_<id>/campaigns`) | **Playwright по Ads Manager UI** |
|---|---|---|
| Стабильность | Версионированный API, официально поддерживается, ломается редко и с предупреждением (deprecation) | UI меняется без предупреждения — классы/разметка обфусцированы, могут поменяться за ночь |
| Риск бана аккаунта | Официальный путь, ToS это разрешает | Facebook ToS формально запрещает автоматизированное взаимодействие с самим UI (не с API) — риск флага/чек-поинта/бана выше, особенно при высокой частоте действий |
| Скорость/надёжность | Мгновенно, атомарные ошибки в JSON | Медленно (секунды на клик/рендер), хрупко, нужны ретраи |
| Обучение/поддержка | Один раз выучил схему полей — работает для всех аккаунтов | Нужно поддерживать «карту кнопок» и чинить её при каждом редизайне |
| Что можно, чего нет | Почти всё, что есть в UI, + то, чего в UI нет | Иногда есть фичи, которых ещё нет в API (edge-cases), но это редкость |

**Рекомендация:** если есть доступ к рекламному аккаунту с правами и можно завести Marketing API приложение — 90% того, что нужно (кампания → адсет → объявление → таргетинг → бюджет → креатив), закрывается через Marketing API быстрее и надёжнее, без риска «сегодня работало — завтра сломалось от редизайна». Playwright имеет смысл только там, где: (а) API-доступа нет и не будет (например, кто-то в команде работает руками и хочет just automate the manual flow), либо (б) нужен конкретный шаг, которого нет в API (например, специфичный UI-виджет).

Если решение — всё равно Playwright (например, потому что API-доступ недоступен или процесс должен один-в-один повторять то, что руками делает баер), дальше — как это спроектировать.

## 1. Архитектура агента

```
upload_plan (Excel/БД, из агента 8)
        │
        ▼
┌───────────────────┐
│  Plan Loader       │  читает строки плана → нормализует в шаги
└─────────┬──────────┘
          ▼
┌───────────────────┐      ┌──────────────────────┐
│  Flow Config        │◄────│  selectors.yaml /json │  «карта кнопок» — версионируется отдельно от кода
│  (login, create      │     └──────────────────────┘
│   campaign, ad set,  │
│   ad, upload creative)│
└─────────┬──────────┘
          ▼
┌───────────────────┐
│  Playwright Runner  │  page object model, ретраи, self-healing selectors
└─────────┬──────────┘
          ▼
┌───────────────────┐
│  Result Writer      │  статус по каждой строке: success/fail, fb_campaign_id, скриншот, лог
└───────────────────┘
```

Ключевая идея: **код одноразовый (написан один раз), а «что где нажимать» — данные** (конфиг), которые можно обновлять без переписывания скрипта. Это и есть ответ на «как его обучать» — обучение агента = редактирование конфига селекторов и флоу, а не кода.

### 1.1 Page Object Model

Один класс/модуль на экран UI: `LoginPage`, `CampaignCreatePage`, `AdSetPage`, `AdCreatePage`, `CreativeUploadDialog`. Каждый метод — одно осмысленное действие («задать дневной бюджет», «выбрать интерес таргетинга», «загрузить видео»), а не набор сырых кликов в скрипте запуска. Это даёт:
- один скрипт запуска на весь план (цикл по строкам), без дублирования логики кликов;
- локализацию исправлений: сломалась загрузка креатива — правишь один метод, а не ищешь по всему коду.

### 1.2 Стратегия селекторов (самое хрупкое место)

FB Ads Manager — SPA с генерируемыми/обфусцированными CSS-классами (`x1n2onr6`, и т.п.) — по ним вообще нельзя опираться, они меняются между рендерами. Порядок предпочтений для Playwright-локаторов:

1. `get_by_role(role, name=...)` — по ARIA-роли и видимому тексту/aria-label (кнопка «Publish», «Next», поле «Campaign name»). Facebook в целом поддерживает accessibility-разметку, это самый устойчивый вариант.
2. `get_by_label(...)` / `get_by_placeholder(...)` — для полей форм.
3. `get_by_test_id(...)` — если у элемента есть `data-testid` (в некоторых частях Ads Manager есть, не везде).
4. `get_by_text(...)` с `exact=True` как последний вариант для элементов без роли.
5. CSS/XPath по структуре — **избегать**, самое хрупкое; использовать только как fallback с явным комментарием «временно, до найденной роли».

Каждый шаг стоит хранить как **список кандидатов-селекторов**, а не один селектор: раннер пробует первый, при неудаче — следующий, и логирует, какой сработал. Это и есть «self-healing» без ML — просто заранее заложенная избыточность.

```yaml
# selectors.yaml (пример структуры, не итоговый файл)
create_campaign:
  open_button:
    - role: "button", name: "Create"
    - text: "Create"
  objective_sales:
    - role: "radio", name: "Sales"
  next_button:
    - role: "button", name: "Next"
```

### 1.3 Сессия и логин

- Логиниться руками один раз, сохранить контекст через `browser_context.storage_state(path="auth.json")`, дальше все запуски стартуют с готовой сессией (`storage_state=auth.json`) — не логиниться каждый раз скриптом (лишний риск чек-поинта/2FA/капчи, а капчу агенту решать нельзя).
- Если FB запросит повторную верификацию (email/SMS код, чек-поинт бизнес-верификации) — агент должен **остановиться и попросить человека** пройти это руками в этом же persistent-профиле (Playwright `launch_persistent_context` с реальным профилем браузера), а не пытаться обходить проверку.
- Хранить `auth.json`/профиль вне репозитория, в `.gitignore` (как уже сделано для `google_credentials.json`).

### 1.4 Идемпотентность и учёт статуса

В `upload_plan` (или в самом Excel) добавить колонки: `upload_status` (pending/in_progress/done/failed), `fb_campaign_id`, `uploaded_at`, `error_message`. Перед каждым запуском строки — проверка: если уже `done`, пропустить. Это защищает от дублей при повторном запуске после сбоя на середине плана.

### 1.5 Логи и трассировка

- На каждый шаг — скриншот (`page.screenshot()`), в лог — что делали, какой селектор сработал.
- Включить Playwright **trace** (`context.tracing.start(screenshots=True, snapshots=True)`) на весь прогон — при падении открываешь `trace.zip` в Playwright Trace Viewer и видишь весь клик-путь визуально. Это критично для FB Ads Manager, где падения почти всегда «UI не там, где ожидали».
- Финальный отчёт по прогону: сколько строк успешно, сколько упало и почему (селектор не найден = сломался UI; FB вернул ошибку валидации = проблема в данных плана; таймаут = сеть/нагрузка).

### 1.6 Темп и защита от детекта автоматизации

- Не кликать мгновенно одно за другим — рандомизированные паузы между действиями (человекоподобный темп), `slow_mo` в Playwright на старте.
- Не гнать десятки кампаний параллельно в несколько вкладок с одного аккаунта — последовательно, по одной.
- Использовать headed-режим (не headless) при первых прогонах — headless-браузеры чаще ловятся антибот-эвристиками, плюс проще дебажить визуально.

## 2. Как «обучать» агента новым флоу (главный вопрос)

«Обучение» здесь не ML — это процесс записи и параметризации ручного флоу.

### Шаг 1 — записать флоу через Codegen
```
playwright codegen https://adsmanager.facebook.com
```
Пройти руками весь путь создания кампании/адсета/объявления так, как это обычно делает баер. Codegen сгенерирует черновой Python-скрипт с локаторами — это черновик, не финальный код.

### Шаг 2 — вычистить и параметризовать
Из сырого codegen-скрипта достать: (а) последовательность экранов/шагов, (б) по каждому полю — какой из них должен браться из строки плана (`country`, `targeting`, `budget`, `creative_number`, `copy`, …), а какой — фиксированный (объектив кампании, дефолтная стратегия ставок и т.п., как в шаблонах `docs/agent8_excel_fb_research.md`). Заменить захардкоженные значения на аргументы функции/поля из плана.

### Шаг 3 — заменить хрупкие селекторы на устойчивые
Codegen обычно генерирует селекторы по тексту/роли из коробки (это хорошо), но иногда — по структуре DOM. Пройтись руками и заменить на `get_by_role`/`get_by_label` там, где можно; вынести в `selectors.yaml`.

### Шаг 4 — тест на sandbox-аккаунте
Прогнать на тестовом рекламном аккаунте (или на кампании с `Campaign Status = Paused`/минимальным бюджетом) **до** прогона на боевых аккаунтах. Facebook даёт возможность создать кампанию и сразу поставить на паузу — это даёт «безопасный полигон» без реального открута бюджета.

### Шаг 5 — зафиксировать флоу как золотой сценарий
Сохранить пройденный трейс (Playwright trace) как референс «как это должно выглядеть», чтобы при будущих сбоях сравнивать: что изменилось в UI относительно эталона.

### Когда FB меняет интерфейс (будет происходить регулярно)
1. Раннер падает на шаге N → в логе видно: «ни один из кандидатов-селекторов для `create_campaign.next_button` не найден».
2. Открыть `trace.zip`, посмотреть, как теперь выглядит экран.
3. Открыть **Playwright Inspector** (`PWDEBUG=1`) прямо на этом шаге, руками навести на нужный элемент, скопировать новый локатор («Pick locator»).
4. Обновить только `selectors.yaml` (или добавить новый селектор в список кандидатов, не удаляя старый — вдруг FB катит A/B редизайна на часть аккаунтов).
5. Прогнать на sandbox-аккаунте перед боевым использованием.

Это и есть «переобучение» агента — быстрый цикл «упал → посмотрел трейс → поправил один селектор в конфиге → перепроверил», без переписывания логики.

## 3. Куда это встраивается в существующий пайплайн

- **Вход:** файл из агента 8 (`output/upload_plan.xlsx`, лист = аккаунт) или строки `upload_plan` из БД (см. `docs/service-architecture.md` §2.2, §7.2).
- **Выход:** обновлённые статусы в `upload_plan`/новая таблица `upload_run` (по аналогии с `analysis_run`) — по каждой строке: `fb_campaign_id`, `status`, `uploaded_at`, `error_message`, путь к скриншотам/трейсу.
- **Место в списке агентов:** логично назвать его **агент 10** — идёт после агента 8 (сборка Excel) и, возможно, после будущего агента 7 (согласование связок), закрывая цепочку «анализ → согласование → сборка плана → **реальная публикация в FB**». Стоит добавить строку в `docs/AGENTS_MASTER_PLAN.md` при следующем обновлении плана.

## 4. Практические риски — проговорить с командой до старта

1. **ToS Facebook** формально запрещает автоматизацию не через API. Официальной защиты от бана это не даёт — риск на аккаунт есть, особенно при большом объёме или высокой частоте действий. Снижение риска: низкий темп, headed-режим, действия только под персистентным профилем с реальной историей логина, никогда не открывать много аккаунтов параллельно с одной машины/IP одновременно.
2. **2FA / чек-поинты бизнес-верификации** — агент не должен и не может их проходить сам (капча/SMS-код) — на этот случай нужен ручной hand-off, не попытка обойти.
3. **Хрупкость к редизайну** — заложить в процесс: раз в спринт/при первом падении — быстрый цикл ревизии селекторов (см. §2), не разовая настройка «и забыли».
4. **Не хранить креды/cookies в репозитории** — `auth.json`/профиль браузера в `.gitignore`, как уже сделано для `google_credentials.json` (см. git-историю проекта).

## 5. Стек и зависимости

- `playwright` (Python) — добавить в `requirements.txt`; `playwright install chromium` при первой настройке.
- Формат конфига селекторов: YAML или JSON (уже используется JSON для `config/knowledge_base.json`, `config/analysis_reading_rules.json` — для консистентности можно взять JSON).
- Логи: обычный `logging` в файл + JSON построчно (легко парсить для отчёта по прогону).
- Опционально позже: обёртка в тот же FastAPI-сервис (`docs/service-architecture.md`) как ещё один route `/api/v1/upload/publish`, который запускает Playwright-раннер в фоне и отдаёт статус по `run_id` — по аналогии с `analysis_run`.

## 6. Реализация (что уже есть в репозитории)

```
src/fb_publish_agent/
    __init__.py
    selectors.json        — карта кнопок (кандидаты-локаторы на каждый шаг), с "_readme" внутри
    locator_utils.py       — resolve()/click_step()/fill_step(): пробует кандидатов по очереди
    plan_loader.py          — читает upload_plan.xlsx (агент 8) по именам колонок; статус-колонки
                              (Upload Status / FB Campaign ID / Uploaded At / Error Message) для идемпотентности
    pages.py                — AdsManagerCreateFlow (Page Object Model): open, set_campaign_name,
                              select_objective, set_daily_budget, set_countries, set_age_range,
                              set_targeting_interest, set_creative_from_library, set_ad_text, publish
    runner.py                — оркестрация прогона: логин-сессия, цикл по строкам плана, dry-run по
                              умолчанию, скриншоты + Playwright trace, human-like паузы между строками
    login_session.py         — разовый бутстрап сессии (ручной логин → storage_state.json)
    publish_from_excel.py    — CLI (main())

run_publish_to_facebook.py   — точка входа: python run_publish_to_facebook.py <upload_plan.xlsx> [флаги]
run_fb_login_session.py      — точка входа: python run_fb_login_session.py
```

### 6.1 Как запустить

1. Установить зависимости и браузер (один раз):
   ```
   pip install -r requirements.txt
   playwright install chromium
   ```
2. Сохранить сессию логина (один раз, и заново — когда FB попросит перелогиниться):
   ```
   python run_fb_login_session.py
   ```
   Откроется видимый браузер → логинишься руками (включая 2FA/чек-поинт) → жмёшь Enter в терминале → сессия сохраняется в `.auth/fb_state.json` (в `.gitignore`, не коммитится).
3. **Откалибровать `src/fb_publish_agent/selectors.json` под реальный аккаунт** — значения в файле сейчас заготовка (см. `_readme` внутри файла), не проверены на живом Ads Manager. Записать реальный флоу:
   ```
   playwright codegen https://adsmanager.facebook.com
   ```
   и заменить кандидатов в `selectors.json` на реально найденные роли/тексты/лейблы (по шагам из §2 этого документа).
4. Прогон в safe-режиме (по умолчанию, **ничего не публикует** — заполняет визард и делает скриншот перед кнопкой Publish):
   ```
   python run_publish_to_facebook.py output/upload_plan.xlsx --account "FacebookUL574 EC Fav" --limit 1
   ```
5. Когда селекторы откалиброваны и скриншоты выглядят верно — реальная публикация:
   ```
   python run_publish_to_facebook.py output/upload_plan.xlsx --live
   ```

Каждый прогон пишет в `output/fb_publish_runs/<run_id>/`: скриншоты по каждой строке, `trace.zip` (Playwright Trace Viewer), `summary.json` (успех/фейл по каждой строке). Статус пишется обратно в сам `upload_plan.xlsx` (колонки `Upload Status`, `FB Campaign ID`, `Uploaded At`, `Error Message`) — повторный запуск того же файла пропускает уже готовые строки.

### 6.2 Известное ограничение

Текст объявления (Primary text / Headline / Link Description) агент 10 подтягивает по значению колонки `Copy` из листа **Ad copy** в `Upluad FB.xlsx` (переиспользует `lookup_ad_copy()` из `src/upload_agent/build_upload_excel.py`, путь берётся из `UPLOAD_FB_EXCEL`/`--reference`) — сам `upload_plan.xlsx` эти тексты не хранит, только имя/ключ Copy. Креатив (`set_creative_from_library`) подставляется по **имени файла** из библиотеки медиа аккаунта в FB (Video/Image file name из агента 8) — план не хранит локальный путь к файлу, так что подразумевается, что креатив уже когда-то был загружен в аккаунт вручную и есть в библиотеке.

## Итог

- Технически реализуемо, но это осознанно более хрупкий и более рискованный (по ToS) путь, чем Marketing API — стоит явно решить, почему не API, до вложения времени в поддержку селекторов.
- Ключевые механизмы устойчивости: Page Object Model, селекторы по роли/тексту с несколькими кандидатами на шаг, persistent-сессия без повторных логинов, идемпотентность по статусу строки плана, скриншоты+trace на каждый прогон, тест на sandbox/paused-кампании перед боевыми аккаунтами.
- «Обучение» = Codegen для записи ручного флоу → параметризация под план → вынос селекторов в конфиг → цикл «упал → посмотрел trace → поправил конфиг» при каждом изменении интерфейса FB.
