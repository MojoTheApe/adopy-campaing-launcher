# Separate process support from the product

Master's global rule applies to every profile: process changes have their own
review, checks and delivery. A consumer installer, application deploy or n8n
publication is required for the actual product outcome, not merely because that
repository distributes a product. The process can itself have versioned tooling,
skill distribution or a service deployment; these remain separate actual results.

## Supported canonical upgrade proof

TT-254 adds the already selected standalone Tracker provider to this same proof.
Both old/new commits must be actual official stable releases; their complete
immutable source trees authenticate the fixed exporter, exact helper bytes and
manifest. The retained Master ancestry and every non-pin descriptor/config/layout
choice stay unchanged. Baseline inputs may change only the exact provider revision.
Unknown exporter algorithms fail closed. The normal whole-outcome and indirect
product-isolation assessment below remains required; this grants no direct-main
route or new policy selection.

`python scripts/task_tracker.py process-support PR_NUMBER` is read-only. In the
engine use `python -m tracker`. It reconstructs the complete immutable diff and
reports content proof separately from independently reviewed task outcome.
`product_delivery: unknown` never means no release is needed. Missing/changed scope,
unsupported content or unavailable provenance cannot authorize process completion.

The bounded first implementation covers Master-generated separated consumers:

- Both standards are exact official published stable Master commits. Their
  immutable compatibility records authenticate the exact Tracker export closure;
  the new record advertises `process_support: [1]`. Public proof needs no private
  Tracker source token. A consumer cannot authenticate its own rehashed helpers.
- Every old/new helper and export record matches the corresponding published
  canonical bytes. Engine pins and descriptor standard/Tracker version pins agree.
- Product identity, execution/context/completion/retry choices, targets, checks,
  authorization and all other descriptor fields remain unchanged. Tracker config
  and the separated layout are unchanged. Only one exact Master Action pin can
  change in the existing descriptor-check workflow; jobs/permissions do not change.
- Old/new template baselines identify those standards, preserve actual rendering
  inputs and every non-process entry, and retain the canonical helper ancestry.
  Regular repository Markdown and existing typed process forwarding files may
  change. Product/runtime knowledge and local scripts, release workflows, packaging,
  dependencies, new policy selections and mixed/unknown files do not qualify.

File location, an upstream version string, a task label or a capability name alone
does not establish this proof. Baseline snapshots and source trees must be complete;
unsafe modes, links, binary/truncated content, changed local helpers and missing
provenance are refused. Raw/older layouts require their reviewed layout adoption
before using this bounded separated-support proof. Arbitrary local automation
requires its own maintained verified isolation contract, not a broader allowlist.

## Independent whole-outcome review

The genuine ordinary source/combined Reviewer reads the complete original task,
including publication and business criteria. Add `process_support` to the existing
independent-review evidence only when the entire singleton outcome is process-only.
The read-only command prints `review_assessment` with schema1, canonical kind,
`outcome: process-only`, exact `proof_sha256` and current `issue_scopes`. Add a
nonempty `report` explaining the full-scope decision and `product_isolation` with
`result: isolated` and nonempty `evidence`. Inspect actual imports, packaging/build
inputs and indirect dependencies: unchanged product files can still consume a
changed canonical helper. Content proof alone does not establish that isolation.
Record through normal
`record-review` preview/apply. This does not acquire ownership or approve a source.
Changed scope/content requires fresh applicable independent review. Even legacy
projects without optional completion policy must retain this exact scope binding.

Keep all incumbent source approval, genuine ownership, frozen composition, Stage,
main admission and required checks. This is not schema1's instruction-only route
or a new direct-main shortcut. Before integration, a proven independently reviewed
process-support outcome selects process delivery without `--deliver` for the
consumer product. Existing explicit product publication scope or a genuine
requested batch/direct delivery is never cancelled, waived or silently satisfied.
It retains ordinary pending delivery and the actual native receipt path.

After the real fully admitted main merge, normal `merged` completion can record
the independently reviewed support result. Its private `process-support` verification
retains the real ordinary admission, canonical proof and whole-scope review. The
public projection says product delivery is not required; it exposes no reports,
session/claims, manifests or private content. A process diff cannot complete an
otherwise unfinished parent. Native acceptance remains required for original
unchecked product/business post-main criteria; preserve frozen Issue bodies.
For legacy projects, ticking already reviewed process criteria after main needs a
fresh independent full-scope support review while the original actual task slot is
retained and no completion was recorded. At least one existing top-level prose
checkbox must be ticked; title, requirements, labels and code examples stay unchanged.
For a staged legacy source, require its retained passing Stage receipt and actual
unchanged main integration before this refresh. The original review/scope remains in history. This narrow
recovery cannot rewrite requirements or substitute for missing product acceptance.

A genuinely completed process-support batch carries `delivery.kind: process` in
its safe projection. The board labels it **Process updated**; it does not report a
consumer product release. Existing product batches retain their delivery labels.

## Compatibility and rollout

### Project-owned process adapters

There are no repository-name exceptions for new process receipts. A project may
explicitly declare its existing process adapters in `delivery.json`:

```json
{"workflow": {"process_support": {"schema_version": 1,
  "control_files": ["scripts/publish.py", ".github/workflows/publish.yml"],
  "verification_files": ["tests/test_publish.py"]}}}
```

The example is an optional part of the existing descriptor, not a replacement
descriptor or a default inherited by new projects. Paths are exact, unique,
bounded and non-executable regular text files; globs, executable plugins, product
paths, canonical helpers and policy files are excluded. Accept the declaration
in its own independently reviewed metadata-only change. That change cannot also
edit the files it authorizes. The project-owned declaration does not alter the
pristine template. A later adapter PR must keep the entire descriptor and Tracker
config unchanged and preserve every Git entry outside the declared files and
normal repository instructions.

This establishes eligibility, not product isolation. Actual source/combined
reviewers still inspect the complete outcome, imports, packaging/build effects
and changed publication controls. Normal admission and configured checks remain;
an actual product-publication request is never waived. A separate tightly bounded
metadata proof also supports explicit instruction schema1-to-schema2 selection
with matching config/descriptor and unchanged checks. Publisher compatibility is
verified before that selection. Publish/install a compatible reader before new
typed receipts. Existing `acl-delivery-governance` receipts remain readable as
historical evidence; the old ACL-specific permission is no longer issued.

Schema1 instruction eligibility/admission, existing delivery profiles and policy
selection are unchanged. Old receipts are not reclassified. Publish compatible
Tracker/portable writers and snapshot readers first, then the exact Master pair
and canonical skill, then separately reviewed consumer support upgrades. An old
reader treats this new private verification as unverified rather than fabricating
delivery; do not deploy writers ahead of its supporting reader. Consumer pins,
ownership, capacities, history and explicit product-release requests stay intact.

## Isolated manual verification tooling (TT-194)

The additive `isolated_verification: [1]` capability does not broaden instruction
schema1 or canonical-support v1. `process-support PR_NUMBER` can inspect a second
bounded candidate: exactly one added manual workflow plus repository instruction Markdown
and `tests/**/test_*.py`. Every other immutable Git entry, including product,
dependencies, scripts, packaging, existing delivery/publication workflows and
selected configuration, must be unchanged. Editing an existing workflow is outside
this initial bounded contract. Unsupported
YAML, automatic triggers, permission overrides, reusable job workflows, self-hosted
runners and masked job failures are refused by the conservative grammar.

This structure is **eligibility, not semantic proof**. A separate actual assessor
must review the complete original Issue and immutable diff, indirect imports,
packaging/build/install/update inputs, scripts, secrets, external calls and actual
side effects. Their `process_support` assessment uses the printed exact proof and
issue scope, with meaningful `report` and `product_isolation` evidence. A workflow
path, read token or successful empty job cannot replace that assessment.

After normal source review, source/batch/Stage/main admission, `merged` recording
and any original unchecked-criterion acceptance, use the same command with
`--evidence-file FILE` to preview, then `--apply` to record the actual result. The
JSON has kind `independent-process-verification`, the actual new `reviewer`, the
retained review's `implementer`, a `report`, the exact `process_support` assessment,
and `workflow_run: {"id": RUN_ID, "attempt": ATTEMPT}`. This is a supplementary
delivery assessment, not source ownership or a new historical approval.

The recorder revalidates the genuine singleton main receipt and its original
scope/review/acceptance, current main inclusion and successful official native
workflow_dispatch attempt. Repository, workflow path/blob, admitted merge and tree,
and all expected successful job names/heads must match. Superseded attempts,
partial/skipped jobs and different successful workflows do not count. Only the
original pending outcome can transition: its full receipt is retained in history;
source reviews, claims, lanes and acceptance records are unchanged. Retry verifies
the same proof and is idempotent. Every genuine publication request in live,
completed or frozen history retains its product delivery; old receipts are never
automatically reclassified. The safe public projection reports process completion
without exposing private assessor/report/run details.

Publish the compatible reader/writers and exact reviewed Tracker/Master pair
before a consumer's separately reviewed support adoption and first new receipt.
Older readers conservatively leave the new proof unfinished. This additive receipt
changes no capacity, optional policy selection, workflow phase or private-state
protocol, and creates no release controller or consumer product publication.

## Existing automatic artifact retention (TT-248)

Task Tracker3.25.0 advertises the separate `artifact_retention_operator: [1]`
capability. This published-source operator supports an unchanged, explicitly
selected official standalone Task Tracker provider. It does not activate newer
consumer helpers, migrate provider pins or broaden the Master-pair authorization
of TT-194. Run it from the clean exact official stable released Tracker checkout,
with `--config` pointing to the consumer's actual original configuration:

```
python -m tracker --config /absolute/consumer/tracker/config.json process-support MAIN_PR --artifact-retention
python -m tracker --config /absolute/consumer/tracker/config.json process-support MAIN_PR --artifact-retention --selected-provider-checkout /absolute/exact-old-provider --evidence-file /absolute/assessment.json
```

The first command only inspects eligibility. The second previews authenticated
recording; repeat with `--apply` only after inspecting that exact result. The old
provider checkout must be clean, official and at the actual selected revision.
Both the operator and selected provider require actual official stable releases
whose tags resolve to their exact commits. A fresh immutable previous-provider
snapshot reconstructs its export closure. Current-main descriptor, configuration,
engine identity, export record and every selected helper must agree. Neither a
consumer-rehashed manifest nor an unpublished newer checkout supplies authority.

The complete diff may modify exactly one existing workflow, changing only one
literal positive `retention-days` value from1–90 to another1–90 under an unchanged
official `actions/upload-artifact@v4` (or exact commit) step. Existing repository
instruction Markdown may accompany it. All other workflow bytes, step inputs,
names, paths, commands, actions, triggers, permissions and remaining Git entries
stay unchanged. Additions, deletions, mode changes, duplicate keys, aliases, tags,
flow mappings, matrices, reusable jobs and ambiguous retention/name expressions
are refused. Run-block lookalikes do not count. Artifact names are literal except
for the bounded `${{ github.run_number }}` substitution. The producer begins with
an official checkout step. Unsupported workflows keep their existing obligation.

Use a genuine new independent whole-outcome assessor, distinct from the original
implementers and combined Coordinator. Their JSON uses kind
`independent-artifact-retention`, the retained review's `implementer`, actual
`reviewer`, meaningful `report`, printed `process_support` assessment with
`product_isolation`, and `workflow_run: {"id": RUN_ID, "attempt": ATTEMPT,
"artifact_id": ARTIFACT_ID}`. Review all original criteria, indirect dependencies
and side effects, including preservation of working releases and rollback. The
operator shares the existing singleton main admission, independent source/combined
review, exact accepted scope, post-main acceptance, pause/correction and publication
veto gates. It never creates admission, closes an incomplete parent or dismisses
any live, frozen or historical genuine product publication request.

Proof may use the original successful admitted combined PR run or its actual main
push; it does not require a new build. The official repository, original PR
head/ref or actual merge/ref, workflow path/blob, all expected successful native
jobs and exact upload step must match. The upload producer's official checkout
log identifies the actual checked-out commit, including a PR temporary merge;
its immutable Git tree must equal the admitted tree. An empty post-merge
`run.pull_requests` array does not invalidate that complete binding. Native upload
logs bind the resolved official action, expanded name, days, artifact ID and
digest. Artifact API provenance must match the run/repository/head; actual live
creation and expiration timestamps must demonstrate the requested duration,
allowing at most60seconds of GitHub timestamp skew. Missing/expired artifacts or
logs, superseded attempts and skipped/partial jobs cannot establish a new result.

At recording, the current main workflow, provider controls and selected helpers
must still match the admitted outcome. Unrelated main descendants are allowed;
a later revert/superseding workflow is refused. Only the exact original pending
receipt can gain the typed supplemental result. Its previous receipt remains in
history, source reviews/acceptance/ownership remain unchanged, and the write uses
the existing state compare-and-swap. An identical verified replay rechecks
authority, scope and current outcome, then preserves the original proof even if
temporary artifacts have since expired. Changed evidence never replaces it.

Deploy the compatible shared snapshot reader **before the first new receipt**.
Older selected consumers preserve the unknown private receipt when writing state,
but their completion/dependency readers conservatively report it unfinished until
supported reader adoption. Do not present that limitation as product delivery or
silently repin the consumer. The new public projection reports process completion
without private evidence. The post-main recorder does not close the GitHub Issue;
after verified native completion, follow the repository's ordinary Issue-close
convention and inspect the fresh board projection. No installer is published.
