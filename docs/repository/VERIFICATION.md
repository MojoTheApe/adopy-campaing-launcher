# Verification policy

Verify process changes separately from product delivery for every profile.
Instructions and isolated task/workflow tooling need relevant checks and
independent review. Assess complete immutable inputs, including indirect product,
build, install and update effects; a directory or label alone is insufficient.
Testing a build or installer does not authorize publishing an unchanged product.
Split mixed changes and use only the pinned supported completion proof.

Read the exact [selected shared guide](TRACKER.md), the [ACL support/cutover plan](EARLY_ADOPTION.md) and the guarded operator mapping in [AGENTS.md](../../AGENTS.md).
Shared contract references retain canonical bodies; `_ACL` documents preserve the original local cutover history and stronger controls.

Follow the [shared verification policy](https://github.com/MojoTheApe/master-repo/blob/6cbc2bbfd5df76fc2f1ad6f285d33a45dd5ff504/docs/verification.md)
at this project's exact standard pin. `delivery.json` defines actual product
commands/required CI names; retain matching Tracker settings, runtime checks and
local exceptions. These compatible local wording clarifications require no new
standard release, pin/helper upgrade or policy selection. Separate fast source
feedback, combined-candidate integration and actual delivery acceptance. Select
by changed risk, not a desired green result.

Keep the project-owned fast/full plan below, with its actual commands,
platforms and distinct truthful result names. Fast feedback is intermediate;
ready handoff and admission need all applicable full coverage. Group related
corrections into a meaningful ready submission on the owned task branch; retain
useful intermediate feedback and normal review fixes. Explain manual expensive
launches or unexpected repeats through existing task/PR/run links. Follow the exact pinned [submission rules](https://github.com/MojoTheApe/master-repo/blob/6cbc2bbfd5df76fc2f1ad6f285d33a45dd5ff504/docs/verification-submission.md).

Preserve the adopted collector's existing bounded reuse rules. Expand context
proof only through reviewed compatible support/adoption; the common policy alone
cannot add an unsupported environment signature. Run missing jobs/platforms.
Preserve independent combined review, any enabled exact stage target and package/production
proof. Inspect passing unchanged evidence before rerunning; add checks for changed
inputs, findings, missing scope or unresolved concerns. A different reviewer or
session does not reset valid tests. Exact head/base/scope review and admission
remain required even when covered test results are reusable.

Existing metadata/linkage concurrency is separate from code suites and cancels
only superseded work for the same PR; preserve admitted integration push evidence.
This describes current behavior, not a request to edit Actions or settings.
A fast success or instruction-only skip cannot
replace missing full coverage. Diagnose failures before retrying. Native failed-job
reruns require actual original successful job/dependency proof supported by the
adopted collector; otherwise use supported bounded complete coverage or stop.
Preserve stricter adopted limits and inspect an uncertain dispatch before another
request. Shared retry/evidence export does not opt ACL in.

For an authorized standard upgrade, use the
[coordinated procedure](https://github.com/MojoTheApe/master-repo/blob/6cbc2bbfd5df76fc2f1ad6f285d33a45dd5ff504/docs/workflow-upgrades.md).
Only the exact compatible Tracker guide supplies commands. A newer standard/skill
cannot activate an unimplemented maintenance or evidence collector.

## ACL checks and preserved boundaries

Follow [WORKFLOW.md](WORKFLOW.md) for affected local regressions, scanner and smoke;
the owner requires the full product suite on hosted CI. Keep the exact required
`descriptor`, `tracker-link`, `ACL verification` and `Installer verification` names,
Linux/Windows selection and the isolated installer/update/recovery acceptance.
Unknown/mixed sources, combined batches, actual stage/promotion, manual and release
contexts retain their complete applicable checks. Read author evidence before
adding reviewer checks; unchanged successful coverage needs no blind local repeat.


### Fast feedback and full verification

ACL's existing **`Classify and check project tooling`** check is tooling fast
feedback. Its `scope` job in `.github/workflows/ci.yml` has a five-minute ceiling
and keeps its exact name, producer annotation and dependencies. It runs these
existing commands after checkout of full history:

```sh
python3 scripts/acl_ci_scope.py --workflow ci.yml
python3 scripts/acl_scan_secrets.py
python3 -m pip install 'pytest>=8,<10' 'PyYAML>=6,<7' cryptography==50.0.1
python3 -m json.tool tracker/config.json > /dev/null
python3 -m json.tool tracker/engine.json > /dev/null
python3 -m pytest --noconftest tests/test_acl_ci_scope.py tests/test_acl_batch_ci_scope.py tests/test_acl_complete_delivery.py tests/test_acl_process_instructions.py tests/test_acl_batch.py tests/test_acl_ci_reuse.py tests/test_acl_ci_workflows.py tests/test_acl_ci_chain.py tests/test_acl_ci_minutes.py tests/test_acl_tracker.py tests/test_tracker_v2.py tests/test_master_adoption.py tests/test_acl_test_platform.py tests/test_ci_layout.py -q
```

The classifier requires the real event/Git context and its existing read token.
Local tooling feedback can use the scanner, JSON checks and this test list with
installed dependencies; it does not fabricate a hosted classifier result.
`--noconftest` belongs to this existing tooling-only suite. Affected product tests
retain their normal isolated machine, library and telemetry fixtures.

Fast feedback omits the complete application/Chromium suite, Windows-only
behavior and startup smoke, full interpreter matrix, installer
build/install/repair/uninstall and published-package acceptance. Its success is
never full product, admission or delivery evidence. `Process instructions` also
requires actual tooling success and remains restricted to its existing
instruction-only eligibility; mixed changes follow the normal source/batch route.

Full applicable admission still requires the distinct exact names `descriptor`,
`tracker-link`, **`ACL verification`** and **`Installer verification`**. The ACL
aggregate requires successful scope/process checks and every applicable selected
Linux/Windows result; explicit non-applicability is separate from proven reuse.
Missing, failed, cancelled or unknown required coverage cannot pass on tooling
success. Ordinary sources retain the conservative affected selection; combined
batches, actual stage/promotion/main, manual and unknown contexts retain all
applicable checks. The existing matrix, exact-tree collector and independent
combined/package acceptance in [WORKFLOW.md](WORKFLOW.md) remain authoritative.

A manual expensive launch needs a concrete reason such as changed relevant inputs,
a diagnosed failure, unresolved coverage or a new integration composition.
Preserve valid passing evidence and required automatic runs. Do not create cosmetic
commits or manual reruns merely to demonstrate these instructions. A candidate push
still starts its normal applicable checks while tooling feedback arrives early.

A PR title/body `edited` event starts linkage feedback only; the existing code
workflows use GitHub's default `opened`, `synchronize` and `reopened` activities.
A new head (`synchronize`) still starts normal candidate verification. A changed
base or integration composition requires fresh relevant evidence and the normal
author/review route; metadata activity does not provide that proof. Editing
metadata neither starts nor cancels product/installer checks. Only a superseded
same-PR run is cancelled; separate PRs and every integration/main/manual run keep
their own identities. No new workflow, job, check name or trigger is added for
this plan. See [GitHub's PR activity defaults](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).
The actual parsed-workflow activity regression is in
`tests/test_acl_ci_workflows.py`; `tests/test_ci_layout.py` exercises the real
aggregate shell and already refuses tooling success with missing required jobs.

Use existing Issue/PR comments and actual run links for a brief unexpected repeat,
confusing transition or manual expensive launch reason. Unknown causes stay unknown;
no per-job register, new form or blocker is needed. The owner will try the normal
flow on real requested tasks; do not create extra sample tasks, paid demos or
scheduled audits for this instruction update. Do not claim savings from written
guidance. Actions/settings/software changes remain outside this task and can be
considered after owner feedback within separately explicit scope; existing
authorization for such work does not need a routine new permission.

ACL's existing `scripts/acl_ci_reuse.py` collector remains unchanged, including its
bounded exact-tree/merged-source rules. TT-107's optional native V1 protocol does
not cover ACL's dynamic YAML, matrices, Windows runners or installer/artifact

alongside main/stage, no feature-branch push runs, and draft structural validation.
Only superseded PR runs cancel; each integration push keeps its own evidence.
The source-only update changes no application, product skills, employee data,
