# Как держать код RPA-агента в актуальном состоянии на машинах всех сотрудников

## Контекст

Компания хочет перевести Agent 10 (RPA-публикация кампаний через
Multilogin + Playwright) из режима "работает только на моей машине,
пока у меня открыт Multilogin" в режим, когда **каждый сотрудник**
запускает кампании со своего компьютера через свои собственные,
уже открытые/залогиненные Multilogin-профили, а дашборд и общая
база данных при этом централизованы (на домене).

Это отдельная задача от `service-architecture.md` (та спека — про
per-customer Docker-инстансы аналитического инструмента, по одному
SQLite на клиента). Здесь речь о **внутреннем** мульти-пользовательском
рабочем месте для одной компании с общими данными и распределённым
исполнением RPA.

Модель: **hub + локальные агенты**.

- **Hub** (на домене) — общий дашборд + общая БД + API постановки
  задач в очередь ("запусти кампанию X для аккаунта Y").
- **Local agent** — процесс на машине каждого сотрудника: опрашивает
  hub, выполняет Playwright/Multilogin локально его же аккаунтами,
  шлёт результат и скриншоты обратно на hub.

Ключевой открытый вопрос при таком разделении: **как код агента
остаётся актуальным на N машинах**, если разработка (как в этой
сессии) идёт быстро и часто ломается на живых прогонах. Ниже — два
рассмотренных варианта с рекомендациями и чек-листами внедрения.

## Рекомендация

1. Начать с **варианта 1 (git-based)** для пилота — не требует
   ничего строить с нуля, реиспользует уже существующий GitHub-репозиторий.
2. Прежде чем вкладываться в **вариант 4 (Intune)** — задать IT ровно
   один вопрос (см. ниже, "Precondition"). Если ответ "да, Intune уже
   используется для внутренних LOB-приложений" — переходить туда после
   пилота. Если инфраструктуры нет — variant 4 откладывается, вариант 1
   остаётся основным дольше.
3. Не смешивать оба механизма одновременно на одном и том же наборе
   машин — на каждом этапе должен быть один источник истины для
   обновлений, иначе они будут конфликтовать друг с другом.

## Вариант 1: Git-based самообновление при запуске

### Как это работает

У каждого сотрудника на машине — локальный клон репозитория.
Скрипт-лаунчер (`start_agent.ps1`) перед стартом агента:

1. `cd` в папку репозитория.
2. `git fetch origin`.
3. Сравнить локальный `HEAD` с `origin/<branch>`.
4. Если отстаёт — `git pull --ff-only` (только fast-forward, никаких
   merge-конфликтов на машине пользователя).
5. Если `requirements.txt` изменился (сравнить хэш файла с
   сохранённым) — `pip install -r requirements.txt --quiet`.
6. Если список Playwright-браузеров изменился — `playwright install`.
7. Запустить процесс агента.

```powershell
# scripts/start_agent.ps1 (набросок)
Set-Location "$PSScriptRoot\.."
git fetch origin agent-stable
$behind = git rev-list HEAD..origin/agent-stable --count
if ([int]$behind -gt 0) {
    $dirty = git status --porcelain
    if ($dirty) {
        Write-Warning "Локальные изменения — обновление пропущено, сообщи в чат команды."
    } else {
        git pull --ff-only origin agent-stable
    }
}
python -m src.fb_ads_rpa.agent
```

### Требования

- Git установлен на каждой машине, есть доступ на чтение к приватному
  репозиторию GitHub — предпочтительно через **персональный** токен
  доступа (fine-grained PAT) или deploy key на человека, а не один
  общий токен на всех, чтобы доступ можно было отозвать точечно.
- Ветка, с которой тянут машины сотрудников — **отдельная стабильная
  ветка** (например, `agent-stable`), НЕ те feature-ветки, где идёт
  повседневная разработка RPA (как в этой сессии — там всё время что-то
  ломается на живых прогонах). Нужен процесс промоушена: протестировал
  → смёржил в `agent-stable` → разъехалось само на все машины.
- Личные секреты и конфиг (`.env`, Multilogin `folder_id` конкретного
  человека, его срез `ad_account_map.csv`) должны жить **вне**
  отслеживаемого git-дерева — например, в
  `%APPDATA%\fb_agents\local.env`, подгружаемом поверх дефолтов из
  репозитория. Иначе `git pull`/`reset` рано или поздно их затрёт.

### Правила безопасности

- Никогда не делать `git reset --hard`, если есть незакоммиченные
  локальные изменения, которые агент сам не контролирует — сначала
  `git status --porcelain`; если "грязно", остановиться и сообщить,
  а не тереть молча.
- Если `git pull` не удался (нет сети, протух токен, конфликт) —
  агент всё равно должен запуститься с тем кодом, что уже есть
  локально, и сообщить об ошибке на hub. Никогда не блокировать
  сотруднику работу из-за того, что проверка обновлений не прошла.

### Кольца раскатки (rollout rings)

1. **Ring 0** — твоя машина, feature-ветки (как сейчас).
2. **Ring 1** — ветка `agent-stable`, пилотная группа 2-3 человека.
3. **Ring 2** — вся компания, после того как Ring 1 отработал стабильно
   несколько дней без сюрпризов.

### Плюсы / минусы

**Плюсы:** дешевле всего в реализации, использует уже готовую
GitHub-инфраструктуру, прозрачно (`git log` показывает, что именно
раскатано).

**Минусы:** нужен git + рабочая авторизация к GitHub на каждой машине;
нет проверки/подписи кода перед раскаткой — у кого угодно с правом
push в `agent-stable` есть возможность мгновенно раскатать код на все
машины разом (нужно ограничить через branch protection + review).

### Чек-лист внедрения

- [ ] Создать защищённую ветку `agent-stable` (branch protection: только
      через approved PR).
- [ ] Написать `scripts/start_agent.ps1` с логикой выше.
- [ ] Вынести все секреты/личный конфиг из отслеживаемого дерева в
      `%APPDATA%\fb_agents\` — описать формат в отдельном
      `docs/agent-local-config.md`.
- [ ] Добавить в `.gitignore`, чтобы никто случайно не закоммитил свой
      личный конфиг.
- [ ] Описать ручное восстановление на случай поломки: "агент не
      стартует — удалить папку репозитория и переклонировать" как
      крайний вариант.
- [ ] Выдать персональные PAT/deploy keys вместо одного общего токена.

## Вариант 4: Раскатка через Intune (управление устройствами)

### Precondition: сначала уточнить у IT

Прежде чем вкладываться сюда, нужно получить ответ на один вопрос:

> Флот компьютеров компании реально состоит под управлением Intune
> (или другого MDM) для установки/обновления внутренних приложений,
> или AzureAD-аккаунт на машине — это только про SSO/M365, без
> политик раскатки приложений?

AzureAD-join сам по себе **не означает** Intune-управление —
это разные вещи. Если у компании нет процесса раскатки внутренних
LOB-приложений через Intune сегодня — этот вариант откладывается
до появления такой инфраструктуры и/или профильного IT-ресурса.

### Как это будет работать (типовой поток Intune LOB app)

1. Упаковать агента как Win32-приложение (формат `.intunewin`) через
   Microsoft Win32 Content Prep Tool — внутри: Python-рантайм (или
   опора на корпоративный стандартный образ), код репозитория,
   Playwright-браузеры, silent-инсталлятор.
2. Загрузить в Intune как Line-of-Business приложение, назначить на
   группу Azure AD (например, "Campaign Managers").
3. Настроить detection rules в Intune (например, сверка версии по
   файлу/ключу реестра), чтобы Intune понимал, когда нужно
   переустановить/обновить.
4. Новая версия: собрать новый `.intunewin`, поднять номер версии,
   загрузить — Intune тихо раскатит на все назначенные устройства
   при следующей проверке (обычно в течение нескольких часов), без
   действий пользователя.
5. Multilogin и другие зависимости (браузеры, драйверы), если их ещё
   нет в стандартном образе компании, нужно будет упаковать и
   раскатать отдельными Intune-приложениями.

### Плюсы / минусы

**Плюсы:** zero-touch для сотрудников, использует уже существующее
доверие устройству и security-политики IT, обновления доедут даже до
тех, кто никогда не вспомнит запустить `git pull`, работает и для
людей, которые вообще не умеют в командную строку.

**Минусы:** заметный lead time (нужен пайплайн упаковки + процесс
IT, скорее всего с привлечением самого IT-отдела, а не только тебя),
более медленный цикл итерации во время активной разработки (интервалы
проверки устройств, не мгновенно как `git pull`), нужен bandwidth/buy-in
от IT, которого может не быть прямо сейчас.

### Чек-лист внедрения (после подтверждения от IT)

- [ ] Получить добро от IT + назначенного контактного лица, которое
      владеет раскаткой приложений через Intune.
- [ ] Написать silent-install PowerShell-скрипт (Python-зависимости +
      Playwright-браузеры + копирование кода агента в фиксированный путь).
- [ ] Упаковать через Win32 Content Prep Tool → `.intunewin`.
- [ ] Определить detection rule (например, сверка содержимого файла
      `VERSION`).
- [ ] Назначить сначала на пилотную AAD-группу, проверить, потом
      расширить на всех.
- [ ] Описать релизный процесс: кто поднимает версию, кто грузит в
      Intune, как откатывать в случае проблемы.

## Итоговое решение по этому документу

План исходит из того, что вариант 1 раскатывается первым в любом
случае — он не зависит от внешних команд. Имеет ли смысл вообще
заниматься вариантом 4, целиком зависит от ответа IT на вопрос про
Intune выше — рекомендуется задать его одним сообщением в IT, не
углубляясь в проработку Intune-варианта до получения ответа.

## Связанные открытые вопросы (вне охвата этого документа)

Эти вопросы поднимались при обсуждении, но не решены — фиксирую,
чтобы не потерялись при дальнейшем планировании:

- Хостинг hub'а (дашборд + общая БД): Azure vs другой облачный
  провайдер vs существующая инфраструктура — не решено.
- Модель логина на общий дашборд: Google/Microsoft SSO vs собственная
  система логин/пароль — не решено.
- Масштаб раскатки: пилот на небольшой команде vs сразу вся компания —
  не решено.
- Привязка "пользователь → его аккаунты/Multilogin-профили" (нужна
  таблица в общей БД, которой сейчас не существует — `ad_account_map.csv`
  не привязан к пользователям).
