# Трекер ACL: спецификация v2

Обновлено 9 сентября 2026 по уточнениям владельца. Документ заменяет предыдущие
варианты A/B одним проектом структуры. **Эта редакция — спецификация будущего
внедрения.** Сейчас на сайте опубликованы защита от пустых обновлений и All;
новые статусы, фильтры и правила приёма идей ещё не включены.

## 1. Цель и принятые ограничения

Владелец управляет проектом через обычный разговор с AI: записывает идеи,
принимает их в план, выбирает порцию задач и поручает последовательное исполнение.
Трекер позволяет быстро понять: что AI делает сейчас, что следующим, что мешает
MVP и что уже завершено. Исполнитель всегда один — AI-агент; поля назначения,
распределение между людьми, аватары исполнителей и персональная загрузка не нужны.

Сохраняются существующие шрифты, светлая/тёмная темы, спокойные цвета статусов,
зелёный In master и характер карточек. Меняются порядок информации, навигация,
группировка и плотность отображения. GitHub Issues остаётся источником задач.
UI показывает данные, фильтрует и раскрывает детали; операции с задачами выполняет
AI в GitHub по поручению владельца. Редактор задач внутри сайта в эту версию не входит.

Основная структура: **проект → модуль → задача**. Статус, приоритет, релиз и
Design — независимые свойства задачи, а не дополнительные уровни вложенности.

## 2. Жизненный цикл задачи

**Idea → Backlog → Todo → In progress → Review → In master**.

| Этап | Значение | Кто/что переводит дальше |
|---|---|---|
| Idea | Предложение записано; решение делать ещё не принято | Владелец принимает идею в Backlog |
| Backlog | Сформулированная задача принята в план, но не выбрана в ближайшую порцию | Владелец выбирает её в Todo либо поручает AI сформировать конкретную порцию |
| Todo | Задача выбрана для выполнения; понятны результат, приёмка и необходимые зависимости | AI берёт её при явном поручении выполнить очередь |
| In progress | AI сейчас выполняет задачу | Подготовлен результат и проверяемый PR |
| Review | Результат проверяется и готовится к слиянию | Полная работа проверена и слита в основную ветку |
| In master | Задача завершена: проверено и слито | Финальный этап |

**Отдельного Done нет: In master и есть «Готово» в процессе владельца.** Нет
дополнительного Release-ready как статуса задачи. В проекте с веткой `main`
финальная подпись настраивается как In main или Merged, внутреннее значение — `merged`.

Создание задачи сразу в Backlog/Todo допустимо, если владелец так попросил.
Для недостающих существенных деталей задача может оставаться в Todo с Blocked
и объяснением, не превращаясь автоматически в In progress. Исправления после
ревью возвращают её в In progress. Возврат завершённой задачи требует явного
нового объёма или регрессии; история и связь с прошлым PR сохраняются.

Blocked — отдельная отметка: этап сохраняется, рядом видны причина, зависимость
или нужное решение. Later убирается: далёкая работа находится в Backlog с
приоритетом. Next убирается: Backlog и Todo теперь различают план и выбранную порцию.

Задачи без программных изменений завершаются проверкой результата: например,
полученный доступ подтверждён, проверка записана. Чтобы не утверждать фиктивный
merge, финальная карточка такой задачи показывает «Готово» и основание завершения;
она входит в ту же конечную группу, а не получает седьмой этап. Кодовые задачи
по-прежнему требуют фактического merge. Отменённые/дублирующие Issues сохраняются
в архиве с причиной и не считаются выполненными.

## 3. Свойства задачи и их представление

| Свойство | Правило | Хранение в GitHub |
|---|---|---|
| ID | Существующие номера и ACL ID неизменны | Issue number, существующий ID в заголовке |
| Модуль | Один основной, по пользовательскому результату | `module:accounts`, `module:campaigns` и т. п. |
| Статус | Ровно один из шести | `status:idea`, `status:backlog`, `status:todo`, `status:in_progress`, `status:review`, `status:merged` |
| Приоритет | High / Medium / Low; у неразобранной идеи может отсутствовать | `priority:high`, `priority:medium`, `priority:low` |
| Тип | Bug / Feature / Improvement / Research / Operations | Одна `type:*`, определяется по содержанию |
| Design | Дополнительная метка для UI/UX-работы, совместимая с любым типом и модулем | `facet:design` |
| Релиз | Необязательный целевой выпуск, например MVP | GitHub milestone; не дублировать именем в статусе |
| Обязательно для релиза | Нужна ли задача для выбранного выпуска | `release:required`; без неё задача в milestone считается дополнительной |
| Блокировка | Причина и зависимость; не заменяет статус | `flag:blocked` + описание/связь с Issue |
| Результат | Критерии приёмки, связанные PR и подтверждение завершения | Тело Issue и ссылки |

Высокий приоритет не равен обязательности для MVP. Задача может быть High, но
относиться к следующей версии; обязательная для MVP задача может ждать зависимости.
При отсутствии указания владельца новая Idea не включается в MVP и не получает
высокий приоритет. При принятии в Backlog приоритет по умолчанию Medium; явное
поручение всегда важнее значения по умолчанию.

В карточке первыми видны ID, короткое название, статус, приоритет и значимые
отметки MVP/Design/Blocked. Технические метки `track:*`, история, подробное описание
и список PR находятся в раскрытии. Поле исполнителя не добавляется ни в UI, ни
в обязательную форму создания.

## 4. Модули и автоматическая классификация AI

| ID модуля | Название | Включать | Не включать автоматически |
|---|---|---|---|
| accounts | Аккаунты и доступ | Аккаунты, страны, профили, роли, подключение, данные аккаунта из Jira | Управление объявлениями — Campaigns; метрики — Data |
| data | Данные и отчёты | Источники метрик BI/API/RPA, периоды, сверка, отчёты и рекомендации | Анализ креатива ради нового материала — Creatives |
| campaigns | Кампании | Билдер, таргетинг, публикация, управление объявлениями, тесты RPA-публикации | Собственно библиотека текстов — Creatives |
| landing | Лендинги и трекинг | LP, размещение, QA, домены, Keitaro, создание трекинг-ссылок | Получение аккаунта из сообщения — Accounts |
| creatives | Креативы и контент | Тексты, библиотека заголовков, брифы, анализ и создание материалов | Встраивание материала в билдер — Campaigns |
| platform | Платформа и эксплуатация | Установка, обновления, общая телеметрия, общие механизмы, сам трекер | Не служит корзиной для любой неоднозначной задачи |

Каталог модулей входит в конфиг проекта: описание, границы и примеры задач.
AI читает его перед классификацией и выбирает модуль по результату для пользователя,
а не по слову «API», «дизайн» или названию файла. Примеры:

- «Новая идея: упростить карточку аккаунта» → Idea, Accounts, Design.
- «Добавить экран очереди AI в трекер» → Idea, Platform, Design.
- «Генерировать заголовки из лучших объявлений» → Idea, Creatives.
- «Управлять доменами трекинга» → Idea, Landing.

Обычно AI классифицирует сам и коротко сообщает результат со ссылкой на Issue.
Если одна идея касается нескольких модулей, выбирает основной по ожидаемому
результату и записывает зависимости; самостоятельные результаты оформляет
отдельными связанными задачами, когда это входит в поручение. Не создаёт копию
одного и того же Issue в каждом модуле.

Если существенной информации недостаточно, идея всё равно сохраняется в Idea
и временно появляется в «Неразобранное» с `flag:needs_classification`. Затем AI
задаёт один точный вопрос. Это техническая подборка, не седьмой постоянный модуль.
Обычные очевидные случаи вопросов не требуют. Новые модули AI не изобретает
при каждом обращении. Перед записью проверяет существующие идеи и задачи на дубли.

## 5. Разговорные команды и обязательные инструкции AI

| Поручение владельца | Требуемое действие |
|---|---|
| «Новая идея: … Добавь в трекер» | Проверить дубли, создать Idea, выбрать модуль/тип/Design, сохранить смысл и вернуть ссылку |
| «Перенеси эту идею в Backlog, приоритет высокий» | Найти конкретный Issue, поставить Backlog + High, сохранить прочие свойства |
| «Это обязательно для MVP» | Назначить milestone MVP и `release:required`; статус не менять |
| «Добавь эти три задачи в Todo в таком порядке» | Проверить критерии и зависимости, перевести выбранные Issues, зафиксировать порядок |
| «Возьми всё из Todo и выполни по очереди» | Зафиксировать состав порции и последовательно выполнить доступные задачи |
| «Покажи, что осталось до MVP» | Отфильтровать обязательные задачи выбранного релиза, которые ещё не завершены, и показать блокировки |
| «Покажи задачи по дизайну с высоким приоритетом» | Совместить Design + High; не менять модуль и статус |

При ссылке «эту идею» AI использует однозначный контекст/ID. Если подходят несколько
Issues, сначала уточняет конкретный, не меняет случайную задачу. Повтор команды
после сбоя не создаёт дубли и не сбрасывает посторонние метки. После записи AI
перечитывает Issue и проверяет отражение результата в UI; кратко сообщает ID,
модуль, статус и заданные владельцем приоритет/релиз.

### Обновление инструкций — обязательная часть внедрения

В той же поставке, что включает новые статусы, нужно:

1. Обновить `docs/DEVELOPMENT_WORKFLOW.md` и добавить единый
   `docs/TRACKER_AGENT_WORKFLOW.md` с командами из этой таблицы, переходами,
   классификацией и порядком выполнения Todo.
2. Подключить единый документ из корневых `AGENTS.md` и `CLAUDE.md`; другие агенты
   должны получать ссылку через свой поддерживаемый файл инструкций. Не плодить
   расходящиеся копии процесса для разных моделей.
3. Обновить шаблоны Issue/PR, установку меток, конфиг и команду завершения задачи
   `scripts/acl_mark_merged.py`. Сохранить проверку полноты задачи перед merged.
4. Включить те же документы в переносимый шаблон. Указать версию схемы и явное
   чтение актуальных правил репозитория до изменения задач.
5. Проверить новый чат на сценариях Idea → Backlog → Todo → merge без ручного
   пересказа правил. Для старых чатов нужно перечитать актуальные инструкции.

Инструкции становятся действующими вместе с поддержкой схемы в трекере. Во время
подготовки спецификации нельзя требовать от агента новые метки, которые текущий
UI ещё не понимает. Критерий завершения внедрения включает инструкции; одной
переделанной страницы недостаточно. Доступ к GitHub и подключение репозитория
остаются необходимыми: файл в Git не может управлять AI, который его не читает.

## 6. Выполнение Todo порциями

Todo — выбранная владельцем очередь, Backlog — весь принятый план. AI не набирает
себе работу из Backlog по собственной инициативе. Добавление в Todo само по себе
не запускает фоновую работу; запуск происходит по поручению владельца.

При запуске AI сохраняет список ID текущей порции и порядок. Новые задачи,
добавленные позже, попадут в следующую порцию, если владелец не расширил текущую.
Порядок: явная последовательность владельца; иначе зависимости, затем приоритет,
затем время помещения в Todo и номер Issue для стабильного разрешения совпадений.
Явный порядок не позволяет выполнять задачу раньше незавершённой зависимости.

AI берёт одну доступную задачу, ставит In progress, реализует и проверяет, проводит
Review, выполняет разрешённый merge по правилам репозитория и ставит In master.
Затем переходит к следующей. Поручение выполнить порцию не отменяет проверки CI,
правила публикации и пределы полномочий; отдельные исключения не переносятся между PR.

Если задача блокируется, AI сохраняет этап и причину Blocked, продолжает следующую
независимую задачу из той же порции. Зависимость из Backlog не начинает без поручения.
Если доступных задач больше нет, сообщает о блокировках. Не выдаёт частично
реализованную задачу за завершённую и не продвигает весь родительский Issue после
слияния только одной подзадачи.

После прерывания новый чат восстанавливает текущий Issue, PR, проверки и оставшуюся
порцию. В одном проекте допускается один активный исполнитель: реализация должна
сохранять состояние запуска в общем для чатов хранилище и атомарно исключать
одновременный захват очереди. Простая проверка метки перед записью недостаточна;
этот случай входит в приёмку. Состояние запуска — технические данные, не поле
«Исполнитель» в пользовательском интерфейсе.

## 7. MVP и готовность к выпуску

MVP — milestone с утверждённым составом. У задач есть признак «Обязательно» либо
они остаются дополнительными. Владелец решает, что входит в обязательный объём;
AI может предложить состав, но не принимает все идеи в MVP автоматически.

Панель MVP показывает, например, **«Обязательные: 7/10 готовы · осталось 3 ·
заблокировано 1»**. Числа здесь иллюстративные: существующим 64 задачам принадлежность
к MVP этой спецификацией не назначается. Считаются уникальные рабочие Issues;
родительские инициативы с меткой `kind:initiative` не увеличивают знаменатель поверх
своих подзадач. Обычный Issue с чекбоксами остаётся одной рабочей задачей.

| Подборка | Условие |
|---|---|
| Всё для MVP | Milestone = выбранный MVP |
| Осталось до MVP | Milestone = MVP AND Required AND не завершено |
| Блокирует MVP | Та же выборка + Blocked |
| Готово для MVP | Milestone = MVP AND финальный этап |

Готовность релиза вычисляется поверх задач: обязательный список непустой, все
обязательные задачи завершены, нет незавершённых обязательных зависимостей или
противоречивых данных. При пустом составе выводится «Состав MVP не задан», а не
«100% готово». При устаревшей синхронизации зелёная готовность не подтверждается.

Рекомендуемая подпись результата: **«Объём MVP готов»**. Если нужен фильтр
Release-ready, это название вычисляемой подборки «Готово для MVP» с пояснением,
а не редактируемая метка и не новый этап задачи. Факт выпуска версии фиксируется
отдельно в записи релиза; достижение In master не запускает публикацию само по себе.
Независимые операции вроде настройки домена или подготовки доступа можно включать
в обязательный список как проверяемые задачи без фиктивного merge.

## 8. Структура интерфейса

### Главный экран: «Работа»

Основной сценарий владельца — увидеть, что происходит и что будет следующим.
Поэтому первым экраном становится текущая порция, а не вся история проекта.
Верхняя навигация содержит **Работа / План / MVP / All**. Это четыре представления
одних Issues, не четыре копии задач. Выбор модуля и дополнительные фильтры сохраняются
и явно показываются; переход в All очищает их все и действительно показывает всё.

```text
ACL Task Wall                                      Синхронизировано …
[Работа]  [План]  [MVP]  [All]

Поиск…     Модуль: Все ▾     Фильтры (2)     Группировать: Статус ▾
Выбрано: Design ×   High ×                         Сбросить фильтры

Сейчас        In progress — одна текущая задача
На проверке   Review — ожидающий проверки результат
Следующие     Todo — компактный список в порядке исполнения
Внимание      Blocked — что препятствует текущей порции
```

Внимание относится к текущей порции и содержит указатели на уже показанные Issues, не дублирует карточки в
счётчиках. Если текущей задачи нет, это прямо написано. Если Todo пуст, показать
«Очередь пуста» и переход к Плану; интерфейс сам не выбирает работу из Backlog.

### План, MVP и All

- **План:** переключатель Idea / Backlog, группировка по шести модулям, поиск,
  приоритет и релиз. Это место принятия решений, а не видимость текущего исполнения.
- **MVP:** выбранный milestone, прогресс обязательного объёма и список того, что
  осталось; можно включить дополнительные или завершённые задачи.
- **All:** все статусы, модули и приоритеты, включая завершённые; исходно раскрывает
  все группы. Поиск и фильтры сброшены. Отменённые/дубли доступны отдельным архивом.
  Повторное нажатие All снова сбрасывает фильтры, даже если режим уже выбран.

Внутри представления фильтр статуса **«Все статусы»** очищает только статус:
например, Design + MVP остаются активными. Он отличается названием и действием
от глобального All, чтобы сложная выборка не сбрасывалась неожиданно.

### Плотность и раскрытие

Для Todo и Backlog нужен компактный вертикальный список, который можно быстро
просмотреть сверху вниз. Один Issue занимает одну строку/компактную карточку;
ID, название, статус, приоритет и важные отметки находятся на постоянных местах.
Текущее оформление карточек и их цвета сохраняются. Раскрытие показывает описание,
приёмку, подзадачи, зависимости и PR. Без нескольких колонок длинных подкатегорий
читателю проще сравнивать соседние задачи и понимать порядок выполнения.

В режиме модулей вложенность ограничена «модуль → задачи». Родительская инициатива
показывается ссылкой в карточке и отдельным раскрытием; не создаёт третий постоянный
ряд колонок. На узком экране — одна колонка, метаданные переносятся, фильтры
раскрываются по кнопке. Цвета, шрифты, иконки статусов и светлая/тёмная темы прежние.

### Фильтры и устойчивость

Доступны статус, модуль, приоритет, тип, Design, milestone, обязательность и Blocked.
Между свойствами действует AND, внутри нескольких выбранных значений одного
свойства — OR. Пример: `(Accounts OR Campaigns) AND Design AND High AND MVP`.
Выбранные условия видны отдельными метками с удалением; результат сопровождается
счётчиком «Показано X из Y». Y — полный объём текущего представления до фильтров.

На небольшом локальном наборе фильтры применяются сразу, без запроса к GitHub на
каждое нажатие. На мобильном несколько условий можно выбрать в панели и применить
одной кнопкой. Пустой результат отличается от сбоя и предлагает сброс фильтров.
Нулевые статусы не исчезают из справочника. Статусы и блокировки обозначаются
текстом/иконкой, не только цветом; все кнопки и раскрытия работают с клавиатуры.

Фильтр статуса хранится отдельно для каждого представления, чтобы переход из
Review в План не оставлял скрытое несовместимое условие. Модуль, приоритет и
Design можно переносить между представлениями, всегда показывая их явно.

Автообновление сохраняет выбранный вид, фильтры, сортировку, раскрытие, позицию
чтения и фокус. Если текущая карточка перестала соответствовать фильтру, показывается
понятное сообщение об изменении статуса; интерфейс не выглядит пустым из-за ошибки.
Нельзя заменять рабочую доску неожиданной пустой выборкой. Настройки просмотра
разделяются по репозиторию и версии схемы, чтобы шаблон не смешивал разные проекты.

## 9. Основания UI/UX-решений

Поиск выполнен 9 сентября 2026. Найден и прочитан сторонний
[Interface Design — SKILL.md](https://github.com/Dammyjay93/interface-design/blob/main/.claude/skills/interface-design/SKILL.md).
Для этого документа применены его принципы: один главный сценарий на экран,
понятная иерархия, повторное использование существующих компонентов и явные
состояния данных. Скилл использован как рабочий источник, глобально не установлен.
Здесь не предлагается новая палитра или визуальный ребрендинг.

Предметная основа решения: идея, очередь, PR, merge, модуль, MVP и зависимость.
Главный отличительный элемент — порядок работы единственного AI и остаток
обязательного объёма MVP. Сохраняется существующий цветовой язык: нейтральный фон,
белые панели, синий для очереди, янтарный для ревью, красный для блокировки,
спокойный зелёный для завершения. Конкретные новые оттенки статусов подбираются
при реализации в пределах этих токенов, без смены общей темы.

Действующие документы [Linear о статусах](https://linear.app/docs/configuring-workflows)
разделяют Backlog и Todo; [документы о milestones](https://linear.app/docs/project-milestones)
показывают отдельное отслеживание и фильтрацию объёма этапа. Это полезные примеры
устройства современного продукта, не требование копировать Linear или переходить
на него. Наши шесть статусов и финальный In master определены процессом владельца.

Подробности по раскрытию опираются на [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/),
а поведение составных фильтров и сохранение контекста — на
[NN/g: User Intent Affects Filter Design](https://www.nngroup.com/articles/applying-filters/).
Это давние принципы удобства, а не новые тренды 2026 года. Для этого трекера
актуальные продуктовые примеры полезнее декоративной моды: предложения ниже
нужно проверять на его реальных задачах.

Три решения для нашей структуры: последовательный список вместо широкой доски
колонок; четыре основных представления вместо ряда всех возможных фильтров;
отсутствие блока исполнителей. Основание каждого — конкретный процесс владельца.

## 10. Переносимый шаблон

Движок отделяется от конфигурации проекта. В шаблоне нет задач ACL, его секретов,
домена или исторического Markdown-снимка как обязательного источника группировки.
Нужны: каталог модулей с примерами для AI, схема статусов/приоритетов/меток,
репозиторий и основная ветка, заголовок, URL, темы и период синхронизации.

Пример будущего конфига; текущий трекер ещё не читает эту схему:

```json
{
  "schema_version": 2,
  "project": {"name": "New Project", "repository": "owner/repo", "base_branch": "main"},
  "workflow": ["idea", "backlog", "todo", "in_progress", "review", "merged"],
  "completion": {"status": "merged", "label": "In main"},
  "priorities": ["high", "medium", "low"],
  "default_backlog_priority": "medium",
  "facets": ["design"],
  "modules": [
    {"id": "accounts", "name": "Accounts & Access", "description": "Accounts, profiles and access", "examples": ["Connect an account"]}
  ],
  "default_view": "work",
  "refresh_seconds": 60
}
```

В комплект входят установка меток и Issue/PR-шаблонов, правила AI, пример размещения
и проверки переходов. Авторизация GitHub конфигурируется отдельно; переносимая
версия не должна зависеть от чужого контейнера OpenClaw. Основной ключ — репозиторий и номер Issue; ACL-префикс остаётся совместимой необязательной подписью. История
проектных данных и версия движка обновляются независимо. Чистая установка второго
проекта должна проверять переносимость без массовой замены строк «ACL» в коде.

## 11. Миграция и порядок реализации

Исходное распределение в приложении сохраняется как проверенный срез из 64 задач,
а не как замороженный список для будущей записи. Перед миграцией перечитать
GitHub, показать новые/изменённые Issues и актуализировать план.

| Старое значение | План преобразования |
|---|---|
| Idea | Idea |
| Next, Later | Предварительно Backlog; действительно начатую работу определить отдельно |
| Review | Review |
| Merged | In master, внутреннее `merged` |
| Blocked | Восстановить основной этап по фактам + `flag:blocked`, сохранить причину |
| Shipped | Конечная группа после проверки исторического основания; сохраняется факт выпуска |
| Closed/неизвестные/конфликтующие метки | Разобрать причину; отмену и неоднозначность не превращать в готовность |
| Числовые area и Design-раздел | Именованные модули; Design переносится в `facet:design` |

Todo не заполняется всем старым Next автоматически. Состав первой порции и
обязательного MVP формируется по отдельному поручению владельца. Существующие
IDs, тексты, чекбоксы, ссылки и история сохраняются. Старые метки удаляются только
после включения всех потребителей новой схемы. Для плана миграции нужен dry run,
проверка конфликтов, повторяемое применение и сохранённая таблица обратных изменений.

Порядок: схема/конфиг и правила AI → поддержка чтения метаданных → представления
и фильтры → команды управления и последовательная очередь → проверка на копии
данных → согласованный план миграции → публикация и проверка нового чата.
Инструкции включаются одновременно с рабочими командами и новой схемой.

**Не включать в эту версию:** отдельный Done, редактор задач на сайте, распределение
между исполнителями, календарь спринтов, оценки в часах/story points, автоматическое
включение всех идей в MVP, массовый merge без проверки полноты задач. Следующие
полезные расширения — сохранённые пользовательские подборки и просмотр зависимостей;
они могут подождать, пока основной процесс станет удобным.

## 12. Критерии приёмки

1. Новая идея через новый чат появляется в Idea с подходящим модулем и ссылкой;
   повтор команды не создаёт дубль, неопределённость не теряет саму идею.
2. «В Backlog, высокий приоритет» меняет только соответствующие свойства;
   добавление MVP/Design не меняет статус. Поле исполнителя отсутствует.
3. Backlog и Todo различимы. Запуск Todo фиксирует порцию, соблюдает порядок и
   зависимости, не берёт новые задачи из Backlog и выполняет одну за другой.
4. Блокировка сохраняет этап и объяснение. Продолжение после прерывания не дублирует
   работу; два чата не захватывают одну очередь одновременно.
5. Полный review + merge завершает кодовую задачу в In master, без Done;
   частичный merge оставляет родителя незавершённым.
6. Обязательный MVP считается по уникальным рабочим задачам; пустой состав,
   незавершённая зависимость и устаревшие данные не дают ложного «готово».
7. Design + Priority + MVP комбинируются; глобальный All очищает все условия,
   «Все статусы» сохраняет остальные. Нулевой результат понятен и обратим.
8. На рабочем экране сразу видны текущая задача, порядок Todo и блокировки.
   В раскрытии доступны приёмка и PR, модуль не требует третьего уровня колонок.
9. На узком экране нет горизонтальной стены колонок; клавиатура, фокус, подписи
   и светлая/тёмная темы работают. Спокойный зелёный и остальная стилистика сохранены.
10. Пустой upstream-ответ не убирает задачи; автообновление сохраняет контекст чтения.
11. AGENTS/CLAUDE ведут к одной актуальной инструкции, разговорные сценарии проверены
    в новом чате; старые правила не требуют лишнего исполнителя или отдельного Done.
12. Второй тестовый проект поднимается из шаблона сменой конфига; в нём нет задач,
    секретов и жёстких привязок ACL. Эта проверка завершает подготовку шаблона.
